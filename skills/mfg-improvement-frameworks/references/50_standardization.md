# 50_standardization — 歯止め（標準化）

改善の成果を残すための道具。**このステップを飛ばすと必ず再発する。**

## QC工程表と作業標準書は役割が違う

**両方そろって初めて歯止めになる。** 片方だけでは再発する。

| | QC工程表 | 作業標準書 |
|---|---|---|
| 答える問い | **何を管理するか** | **どうやるか** |
| 読む人 | 管理側（工程管理・品質保証・監査・取引先） | 作業者 |
| 単位 | 全工程を1枚で俯瞰 | 1工程・1作業ごと |
| 中身 | 管理項目、管理基準値、測定方法、頻度、記録方法、異常時の処置 | 作業手順、動作、使用する治具、判断基準、安全上の注意 |
| 欠けると | 管理項目が決まらず、異常を検出できない | 手順が属人化し、標準どおりに作業されない |

対策を反映するときは、**両方のどこに何を書くかをセットで示す。**
「QC工程表に追加する」だけでは、現場は何をすればよいか分からない。

## 1. QC工程表

原材料の入荷から出荷までの全工程と、各工程の管理方法・基準値・責任者を一覧にした図表。
**4M変更管理のベースとして機能する。**

### 必須項目

| 区分 | 内容 |
|---|---|
| 工程の流れ | 全製造工程、作業名、フローチャート |
| 管理項目 | 品質に影響する加工・製造条件（管理特性）、品質の評価につながる特性値（品質特性） |
| 管理方法 | 機械・設備・材料、管理者の条件、検査・測定方法、記録方法、異常時の対処方法 |

### 管理特性と品質特性の違い

| | 意味 | 例 |
|---|---|---|
| 管理特性 | 工程で**制御する条件** | 機械の回転数、加熱温度、圧力 |
| 品質特性 | 工程の**結果として得られる値** | 製品の寸法、重量、外観 |

**両方を定量で管理する。** 品質特性だけ見ていると、異常が出てから気づくことになる。

### 位置づけ
- 作業標準書の基になる
- ISO9001 で求められる品質計画書に相当する
- 取引先への製造体制の説明に使える

工程フローチャートは JIS Z8206 の工程図記号（加工・検査・運搬・停滞）を使うのが望ましい。

### 異常時の使い方
1. QC工程表どおりに作業されていたかを確認する
2. 守られていなかった → 遵守の徹底（教育・仕組み）
3. **守られていたのに異常が出た → QC工程表そのものを見直す**

### 様式
決まった様式はない。テンプレートは `assets/qc-process-table.xlsx` を使う。

## 2. 作業標準書

QC工程表を各工程の具体的な作業手順に落としたもの。

### 記載すべきこと
- 作業手順（順序と動作）
- 使用する設備・治具・材料
- 加工条件・判断基準
- 異常時の処置
- 安全上の注意

### 要点
- **属人化を防ぐことが目的。** 「熟練者なら分かる」表現を避ける
- 写真・図を入れる
- 継続的に見直す。現物と乖離した標準書は守られなくなる
- **QC工程表で決めた管理項目・基準値と対応させる。** 対応が取れていないと、
  管理側が求める値と作業者が見る値が食い違う

## 3. 4M変更管理（変化点管理）

各プロセスにおける4Mの変更（変化点）を管理し、品質を保つ取り組み。
ISO9001:2015 に「変更の管理」として規定されている。

### 進め方

1. **変化点の洗い出し** — 4M × 3H で展開する（`20_factor-axes.md`）
2. **優先順位付け** — 品質・他プロセスへの影響度、発生頻度、推定損失で評価する
3. **影響範囲の明確化** — 変化点が何に波及するかを特定する
4. **対処方法とルールの策定** — 記録方法を含めて決める
5. **見える化** — 変化点の状態が現場で分かるようにする

### 大前提

**変化点を多発させない工程に改善することが先。** 管理対象が多すぎると管理そのものが破綻する。

### 異常発生時の備え

予測できない事態は必ず起こる。以下を事前に定める。

- 異常・ヒヤリハット発覚時の報告ルール
- 暫定的な対応方法
- 原因究明と再発防止策の立案
- 再標準化と作業員への共有・再教育

### 変化点の例
4Mそれぞれの具体例は `20_factor-axes.md` の「変化点の例」を参照。

## 4. なぜなぜ分析

**ひとことで**：「なぜ」を繰り返して真因に到達する。**要因解析で使う道具。**

**こう言われたら使う**
> 「同じ問題が再発する」「対策したのに効かない」「表面的な対策で終わっている気がする」

**こういうときは使わない**
- 要因がまだ洗い出せていない → 先に特性要因図（要因解析）
- 事実の裏付けが取れない → 推測の連鎖になる。データを集めてから

**必要なもの**：具体的な事象1つ。各段で確認できる事実・現物。

**分かること**：対策可能なレベルの真因。

**手順**
1. 事象を具体的に書く（「不良が出た」ではなく「A工程で寸法が上限を0.3mm超えた」）
2. 「なぜそうなったか」を1段掘る
3. 掘った内容が事実か推測かを区別する
4. 対策可能なレベルに達したら止める（5回は目安。回数に意味はない）

**実務での見極め**

**発生原因と流出原因を必ず2本立てで掘る。**

| | 問い |
|---|---|
| 発生原因 | なぜ不良が作られたのか |
| 流出原因 | なぜ検査で止められなかったのか |

発生原因だけ対策すると、次の不良が客先へ流れる（`70_cases.md` ケース3）。

- 「だから」で逆読みして検証する。繋がらなければ論理が飛んでいる
- 各段で複数の「なぜ」が出ることもある。枝が1本しかないのは掘り方が浅い

**よくある失敗**

| 症状 | 原因 | 対処 |
|---|---|---|
| 「注意力が足りなかった」で終わる | 人の責任に帰着させている | 仕組み側の要因を掘る |
| 途中で論理が飛ぶ | 検証していない | 逆読みで確認する |
| 対策が教育だけになる | 真因に届いていない | もう1〜2段掘る |

## 5. ECRS

**ひとことで**：作業改善を検討する順序の原則。**対策立案で使う道具。**

**こう言われたら使う**
> 「作業を効率化したい」「工数を減らしたい」「この確認作業、意味あるのか」

**こういうときは使わない**
- 品質問題の原因が未特定 → 先に検証
- 作業そのものが対象でない（設備・材料の問題）→ 5Eで検討する

**必要なもの**：対象となる作業の手順。

**分かること**：改善の余地と、その大きさ。

**手順**：この順で検討する。

| 順 | 原則 | 問い | 効果 |
|---|---|---|---|
| 1 | **E**liminate（排除） | やめられないか | 最大 |
| 2 | **C**ombine（結合） | まとめられないか | 大 |
| 3 | **R**earrange（順序変更） | 順序を変えられないか | 中 |
| 4 | **S**implify（簡素化） | 簡単にできないか | 小 |

**実務での見極め**
- **排除から検討する。** いきなり簡素化から入ると、そもそも不要な作業を効率化してしまう
- 「この作業をやめたら何が困るか」を最初に問う。答えられなければ排除できる
- 品質のための確認作業は排除できないことが多い。その場合は Simplify（チェックリスト1枚に集約）へ（`70_cases.md` ケース3）

**よくある失敗**

| 症状 | 原因 | 対処 |
|---|---|---|
| 効果が小さい改善ばかり | 簡素化から始めた | 排除に戻る |
| 排除して品質が落ちた | 作業の目的を確認していない | 何のための作業か先に問う |

## 6. SDCA

標準を維持するサイクル。改善（PDCA）で得た成果を、ここに引き渡して定着させる。

```
Standardize（標準化）→ Do（実行）→ Check（検証・評価）→ Action（改善）
```

| 段階 | やること |
|---|---|
| Standardize | 効いた対策を作業標準書・QC工程表に反映する |
| Do | 標準どおりに実行する。関係者に教育する |
| Check | 標準が守られているか、効果が持続しているかを確認する |
| Action | 守られていなければ仕組みを直す。標準に無理があれば標準を直す |

**PDCAだけを回し続けると成果が元に戻る。** 改善の終点は必ず標準化。

# 70_cases — ケースライブラリ

**判断の過程を再現するためのファイル。** 手法の定義は他ファイルにある。ここにあるのは
「その場でどう考えたか」だけ。

利用者の案件に近いケースを1つ選び、**流れをなぞりながら利用者の言葉に置き換える。**
ケースの文章をそのまま出力しない。

## 目次

## ケース1：寸法がばらつく

### 状況

> 「A工程の外径がばらつく。規格は φ10.00 ±0.05 なんだけど、たまに外れる。
> 測定データは3ヶ月分、Excelにある」

### 最初に見たもの

**データの中身を先に見た。** 列は 日付／号機／作業者／材料ロット／実測値。420行。

この時点で判断できたこと。

- 実測値がある → **合否ではなく数値**。ばらつきの形が見える
- 号機・作業者・ロットがある → **層別できる**
- 420件 → ヒストグラムにも層別にも十分

### 捨てた選択肢

**いきなり特性要因図を描かなかった。** 要因を挙げても、この段階では全部が仮説。
層別すれば10分で「差があるかないか」が分かる。**先に事実を見る方が早い。**

### 流れ

**要因の洗い出し** — 飛ばした。層別キーが最初から揃っていたため。

**重点の絞り込み** — ヒストグラムを描いたら、**山が2つ**あった。
これは「異なる条件が混ざっている」サイン。層別すべき合図。

号機で層別 → 1号機と2号機で中心がずれていた。1号機は φ10.02、2号機は φ9.98。
作業者・ロットで層別 → 差なし。

**検証** — 号機別のヒストグラムを重ねて描き、2つの山が号機の差で説明できることを確認。
念のため時系列（管理図）も見たが、どちらの号機も安定していた。

つまり **「ばらつきが大きい」のではなく「2台の設定が違う」** 。

**対策の立案** — 5Eで検討したところ、Education（作業者教育）は不要と判明。
Engineering（設定値の統一と定期校正）が本筋。

**標準化・定着** — QC工程表の管理項目に「号機ごとの設定値」を追加し、
校正頻度を明記した。

### 押さえたポイント

| 段階 | ポイント |
|---|---|
| 絞り込み | **ふた山を見たら層別する。** これは反射で動いてよい |
| 絞り込み | 差が出なかったキー（作業者・ロット）も記録する。「調べて差がなかった」は成果 |
| 検証 | 中心ずれとばらつき拡大は**対策が真逆**。どちらかを必ず判別する |

### なぜ他の道具でなかったか

| 使わなかった道具 | 理由 |
|---|---|
| 特性要因図 | 層別で答えが出た。要因の網羅は不要だった |
| 散布図 | 対になる連続量がなかった（号機は分類であって量ではない） |
| パレート図 | 項目別の件数を比べる場面ではなかった |

### 落とし穴

**規格内に収まっているデータを捨てないこと。** 不良品だけ集めるとばらつきの全体像が見えない。
良品も含めた全数または抜取のデータが要る。

## ケース2：ヒヤリハットが集まったが打ち手が決まらない

### 状況

> 「ヒヤリハット報告が今月40件上がってきた。多いのは『不注意』『確認不足』。
> どこから手を付ければいいか分からない」

### 最初に見たもの

**内容そのものを読んだ。件数を数える前に。**

- 「不注意」「確認不足」が28件
- 「床が滑る」が2件
- 「表示が見づらい」が3件
- その他7件

### 捨てた選択肢

**パレート図を描かなかった。** 描けば「不注意 28件」が最大になり、
対策は「注意喚起の徹底」になる。これは**毎年やって効果が出ていない対策**。

理由は、「不注意」が**分類ではなく結論**だから。パレート図は分類が適切な場合にだけ機能する。
`30_qc7.md` にある「その他が最大になったら分類をやり直す」と同じ現象が起きている。

そして重要なのは、**「床が滑る」は2件しかないが、対策すれば確実に減る**という点。
数の多寡と、対策の効きやすさは別物。

### 流れ

**要因の洗い出し** — 親和図。40件の報告を1件1枚のカードにして、似たもの同士を集めた。
**分類基準は先に決めない。** 「不注意」という枠を先に作ると、そこに全部吸い込まれる。

集まった結果、こういうグループになった。

- 足元・通路に関するもの（滑る、つまずく、暗い）
- 表示・合図に関するもの（見づらい、聞こえない、紛らわしい）
- 手順に関するもの（省略した、順番が違った）
- 体調・時間帯に関するもの（夜勤明け、繁忙期）

**「不注意」というグループは消えた。** どのカードも、読み直せばもっと具体的な状況が
書かれていたため。

**重点の絞り込み** — 4グループをマトリックス図で評価。
軸は 発生頻度／被害の大きさ／対策の実現性。足元グループが最も対策しやすいと判明。

**検証** — 安全工学の4M（Man / Machine / Media / Management）で分解。
足元グループはほぼ Media（作業環境条件）に集中していた。

**対策の立案** — 系統図で対策を展開。
5Eで見ると Environment（床材・照明）と Engineering（手すり・区画）が中心。
Education は不要ではないが、優先順位は下。

**標準化・定着** — 5S点検表に「床面の状態」を項目として追加した。

### 押さえたポイント

| 段階 | ポイント |
|---|---|
| 洗い出し | **分類軸を先に決めない。** 決めた瞬間に仕分け作業になり、新しい構造が見えない |
| 洗い出し | 「不注意」「確認不足」は結論であって分類ではない。もとの記述に戻る |
| 絞り込み | **少数意見を件数で切り捨てない。** 対策の効きやすさで評価する |
| 検証 | 安全が絡むので分解軸は**安全工学の4M**。製造品質の4Mではない |

### なぜ他の道具でなかったか

| 使わなかった道具 | 理由 |
|---|---|
| パレート図 | 分類が不適切な状態で描くと誤った結論に至る |
| 特性要因図 | 特性（結果）が1つに定まっていない。40件は別々の事象 |
| 連関図 | 要因が相互に影響し合っている状況ではなかった |

### 落とし穴

**親和図を作る作業を1人でやらないこと。** 報告した本人が持っている文脈が抜け落ちる。
Claudeが内容を想像して埋めるのは論外。カードは現場の言葉のまま扱う。

## ケース3：客先クレームが再発する

### 状況

> 「同じ不良で客先から2回クレームが来た。1回目に対策したはずなのに」

### 最初に見たもの

**1回目の対策内容と、その後の記録。**

- 対策：作業者への再教育を実施
- 標準書の改訂：なし
- QC工程表への反映：なし
- 効果確認：実施したが、期間が2週間だけ

これで**再発の理由はほぼ確定**した。標準化していない。

### 捨てた選択肢

**原因追究をゼロからやり直さなかった。** 1回目で特定した原因は妥当だった。
問題は原因ではなく、対策の定着。

### 流れ

**要因の洗い出し** — なぜなぜ分析。ただし**2本立て**で行った。

発生原因の系統

> なぜ不良が作られたか → 加工条件が標準から外れた → 段取り替え後に確認していない
> → 確認する手順が標準書にない

流出原因の系統

> なぜ検査で止められなかったか → 抜取検査で当たらなかった
> → 段取り替え直後を重点検査する取り決めがない

**2本目が1回目の対策で抜けていた。** 教育は発生側にしか効いていない。

**重点の絞り込み** — 両方の系統の末端が「標準に書かれていない」に収束した。

**検証** — 段取り替えの記録と不良発生日を突き合わせたところ、
不良は全て段取り替え当日に発生していた。仮説が裏付けられた。

**対策の立案** — ECRSで検討。
確認作業を Eliminate はできない。Simplify（チェックリスト1枚に集約）を採用。
5Eでは Enforcement（標準書化）と Engineering（治具で条件を固定）を組み合わせた。

**標準化・定着** — ここが本題。

- 作業標準書に「段取り替え後の条件確認」を追加
- QC工程表の管理項目に「段取り替え後の初品検査」を追加
- 4M変更管理のルールに「段取り替え＝Methodの変化点」として登録
- 効果確認の期間を3ヶ月に延長

### 押さえたポイント

| 段階 | ポイント |
|---|---|
| 洗い出し | **発生原因と流出原因を必ず分ける。** 片方だけでは客先に流れ続ける |
| 洗い出し | なぜなぜは「だから」で逆読みして検証する。繋がらなければ論理が飛んでいる |
| 標準化 | **再発案件は標準化が本体。** そこまでを丁寧にやっても標準化が空なら3回目が来る |
| 標準化 | 効果確認の期間が短いと「効いた」と誤認する |

### なぜ他の道具でなかったか

| 使わなかった道具 | 理由 |
|---|---|
| 特性要因図 | 原因は1回目で特定済み。網羅的な洗い出しは不要 |
| パレート図 | 対象がすでに1項目に絞られている |

### 落とし穴

**「教育を徹底する」で終わらせないこと。** 人は入れ替わる。
仕組み（Engineering / Enforcement）に落ちていない対策は、担当者が変わった時点で消える。

## ケース4：ラインを変えてから不具合が出る

### 状況

> 「先月ラインのレイアウトを変えた。それから組付け不良が増えている。
> 原因はレイアウト変更だと分かっているが、元に戻すわけにはいかない」

### 最初に見たもの

**「原因は分かっている」という発言の根拠を確認した。**

- 不良の増加開始日 = レイアウト変更の翌日
- 他の変更（人・材料・条件）は同時期になし
- 変更前の水準には問題がなかった

根拠は十分。**ここで型が変わる。**

### 型の判定

| 問い | 答え |
|---|---|
| まだ起きていないリスクか | いいえ（すでに発生） |
| 現状復帰か、水準の引き上げか | 現状復帰 |
| **原因は分かっているか** | **はい** |

→ **施策実行型**。問題解決型から原因追究（ステップ5）を省略する。

**これがケース1〜3と決定的に違う点。** 原因を探す時間を使わない。

### 流れ

**要因の洗い出し** — 4M × 3H で変化点を展開。「Method の変更」に該当。
そこから具体的に何が変わったかを洗い出した。

- 部品棚の位置が作業者の背面になった
- 作業動線が2m伸びた
- 手元の照度が下がった

**重点の絞り込み** — 3つのうちどれが不良に効いているかをマトリックス図で評価。
不良の種類（部品の取り違え）から、部品棚の位置が最有力と判断。

**検証** — ここは**簡易に済ませた**。原因が既知の型なので、深追いしない。
取り違えた部品の組み合わせを確認したところ、隣接する棚のものだった。裏付け完了。

**対策の立案** — ECRSで検討。

- Eliminate：不要な移動をなくす → 棚を作業者の正面に戻す
- Simplify：部品の色分け・形状違いで取り違えを物理的に防ぐ

5Eでは Engineering（ポカヨケ）が中心。

**標準化・定着** — レイアウト変更を4M変更管理の対象として登録。
「Method の変化点」として、次回の変更時に事前レビューを行う手順を追加した。

### 押さえたポイント

| 段階 | ポイント |
|---|---|
| 型 | 「原因は分かっている」は**根拠を確認してから信じる**。思い込みなら対策が空振りする |
| 洗い出し | 変化点がある案件は、白紙の特性要因図より **4M × 3H が速い** |
| 標準化 | 今回の再発防止だけでなく、**次の変更にも効く仕組み**にする |

### なぜ他の道具でなかったか

| 使わなかった道具 | 理由 |
|---|---|
| 特性要因図 | 原因が既知。網羅的な洗い出しは時間の無駄 |
| 連関図 | 要因が絡み合っていない。単一の変化点が起点 |
| ヒストグラム・管理図 | 計数値（取り違え件数）であり、ばらつきの形を見る対象ではない |

### 落とし穴

**「原因が分かっている」を検証せずに施策実行型を選ぶと、丸ごと空振りする。**
迷ったら問題解決型に倒す方が安全。

## ケース5：新しい工程を立ち上げる

### 状況

> 「来月から新機種の生産を始める。工程は新設。トラブルを事前に潰しておきたい」

### 最初に見たもの

**データがないことを確認した。** 生産していないので当然。
ここで**定量の道具は全て使えない**と確定する。

### 型の判定

まだ起きていないリスクへの備え → **未然防止型**。

### 捨てた選択肢

**パレート図・ヒストグラム・管理図を検討すらしなかった。** 過去の類似機種のデータを
流用する案も出たが、工程が違うため参考程度に留めた。

### 流れ

**要因の洗い出し** — 2段構えで洗い出した。

まず 4M × 3H。新工程は**全てのマスが「初めて」**に該当する。
これ自体が「最も危険な状態」であることを示している。

次に特性要因図。ただし通常と向きが違う。
背骨に「起こりうる不具合」を置き、大骨に4Mを立てて、**まだ起きていない事象**を想定した。

**重点の絞り込み** — マトリックス図で評価。軸は3つ。

- 発生の可能性
- 起きたときの影響
- 気づけるか（検出しやすさ）

**3つ目が重要。** 発生頻度が低くても、気づけない不具合は客先に流れる。

**検証** — ここは弱い。実データがないため、
類似工程の実績・作業者の経験・設備メーカーの情報で補った。
**確からしさが低いことを明記して進めた。**

**対策の立案** — 系統図で予防策を展開し、PDPCで「それでも起きた場合」の経路を描いた。
未然防止では PDPC が本領を発揮する。想定外は必ず起きるため。

**標準化・定着** — 立ち上げ前にQC工程表とチェックシートを作成。

- QC工程表：管理項目と基準値を仮置きし、**立ち上げ後に見直す前提**で作る
- チェックシート：層別キーを多めに入れる。何が効くか分からないため

### 押さえたポイント

| 段階 | ポイント |
|---|---|
| 検証 | **検証が弱いことを隠さない。** 推測を事実のように扱わない |
| 絞り込み | 「気づけるか」を評価軸に入れる。流出リスクは発生リスクと別 |
| 標準化 | 立ち上げ時のチェックシートは**層別キーを多めに**。後から追加できない |
| 標準化 | QC工程表の基準値は仮。立ち上げ後の実データで必ず見直す |

### なぜ他の道具でなかったか

| 使わなかった道具 | 理由 |
|---|---|
| QC7つ道具全般 | データが存在しない |
| 連関図 | 想定の域を出ない要因を絡めても精度が上がらない |

より体系的な未然防止手法（FMEA・FTA・DRBFM）はこのスキルの範囲外。
本格的にやるならそちらを勧める旨を伝える。

### 落とし穴

**推測で作った特性要因図を、事実として扱わないこと。**
立ち上げ後の実データで必ず検証し直す。

## ケースの使い方

1. 利用者の状況に最も近いケースを1つ選ぶ
2. 「最初に見たもの」と「捨てた選択肢」を、利用者の案件に当てはめる
3. 段階の流れをなぞりながら、**利用者の工程名・数値・言葉に置き換える**
4. ケースの文章をそのまま出力しない

**完全に一致するケースはない。** 複数のケースをまたぐことも多い。
その場合は、どのケースのどの部分を借りたかを明示する。

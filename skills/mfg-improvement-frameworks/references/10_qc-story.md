## 1. 型の選定

**選ぶのは「主たる型」1つ。** 排他ではない。部分的に他の型を借りるのが実務の姿（第6章）。

| 問い | Yes | No |
|---|---|---|
| Q1. まだ起きていないリスクへの備えか | 未然防止型 | Q2へ |
| Q2. 現状復帰ではなく、今より上の水準を目指すか | 課題達成型 | Q3へ |
| Q3. 原因はすでに分かっているか | 施策実行型 | 問題解決型 |

**両方に当てはまる場合は問題解決型に倒す。** 最も手順が多く、他の型はその部分集合か
差し替えで表現できるため、後から絞る方が安全。

### 問題と課題の違い

| | 問題 | 課題 |
|---|---|---|
| 定義 | あるべき姿と現状のギャップ | ありたい姿と現状のギャップ |
| 例 | 不良率が基準の0.5%を超えた | 不良率を業界最高水準の0.1%にしたい |
| 型 | 問題解決型／施策実行型 | 課題達成型 |

**「不良を減らしたい」だけでは判別できない。** 基準値に戻すのか、基準そのものを上げるのかを確認する。

## 2. 問題解決型（代表的な並び）

最も標準的。現在発生している問題を、データで原因を追究して解消する。

**以下の8ステップは代表的な並びであって、順番固定の手順ではない。**
ステップは部品で、**順番・回数・有無は案件で組み替える**（`SKILL.md` 組み立て手順）。

| 組み替え | 例 |
|---|---|
| 繰り返す | 現状把握を2回行う（規模をつかむ → 要因解析 → 仮説を検証する） |
| 飛ばす | 原因が既知なら要因解析を飛ばす（施策実行型） |
| 入れ替える | 層別できるデータが最初からあれば、要因解析の前半より先に層別する |

**8 歯止め（標準化）だけは飛ばせない。** ここを飛ばすと再発する。

**各ステップの末尾に「この道具で得たもの」「次にやること」を書く。**
ここが書けないステップは実質的に飛ばしている。
ステップ間で何をどう変換して渡すかは `90_handoff.md`。

### ステップ1：テーマ選定

- 現場の問題を洗い出し、取り組む対象を1つに絞る
- 選定基準：影響度（QCD）／緊急度／実現可能性
- 道具：パレート図（どこが大きいか）、親和図（意見を整理する）

**テーマが抽象的だと以降が全て破綻する。** 「品質を上げる」ではなく「A工程の寸法不良を減らす」まで絞る。

#### 前提を確定してから次へ進む

**ここが曖昧なまま進むと、以降のステップが全部ずれる。** 3つを先に固定する。

| 確定するもの | 悪い例 | 良い例 |
|---|---|---|
| **不良モードの定義** | 塗装不良 | **ムラ**（膜厚が不均一）と**たれ**（膜厚過多で塗料が流れる）は別。発生の仕組みが違うので、どちらを扱うか決める |
| テーマ | 品質を上げる | 塗装ラインの塗装ムラを減らす |
| 対象範囲 | 全工程 | A工程、6〜8月、機種X |

**似た不良モードを1つのテーマに混ぜない。** 発生の仕組みが違えば要因も対策も違う。
混ぜると特性要因図の軸がぶれ、どの要因がどちらに効くのか分からなくなる。

#### 目標は2種類ある。同じ語で書かない

**テーマ選定の時点で与えられる目標と、ステップ3で決める目標は別物。**
同じ「目標」と書くと、どちらの話をしているか読み手に伝わらない。

| | 方針目標 | テーマ目標 |
|---|---|---|
| いつ決まるか | ステップ1より前（上位から与えられる） | **ステップ3**（自分で決める） |
| 範囲 | 部門・工場全体 | このテーマの対象範囲だけ |
| 例 | 工場全体の不良率を年度内に半減 | 塗装ムラを 45件→17件（四半期あたり、12月末） |
| 役割 | テーマを選ぶ判断材料 | 活動の達成基準。効果確認はこれと比べる |

**テーマ目標は方針目標の内訳になっていること。** つながっていないテーマは、
達成しても方針目標に効かない。つながりは計算で示す（`90_handoff.md` 第7章）。

### ステップ2：現状把握

**現状把握は目的の違う2種類がある。** 同じ名前で呼ぶが、置く場所も使う道具も違う。

| | 規模をつかむ | 仮説を検証する |
|---|---|---|
| 置く場所 | **目標設定の前** | **要因解析の後** |
| 決める判断 | どの不良が・どれだけ・どこに出ているか。目標の起点 | 挙げた要因の候補が本当に効いているか |
| 主な道具 | チェックシート、パレート図、層別 | 層別、散布図、追加のデータ取り |
| 出力 | 現状値（件数・母数・率） | 真因（残した候補）と、外した候補とその理由 |

2つ目は要因解析の後半（検証）と呼ばれることもある。呼び方より、**何を決めるための
現状把握かを先に書く**ことが大事。候補を真因と呼んでよいのは検証の後（`90_handoff.md` 第4章）。

- 事実をデータで確認する。推測を混ぜない
- **5W＋1H** で事実を漏れなく押さえる（下記）
- 道具：チェックシート、層別、パレート図、ヒストグラム、管理図

#### 5W＋1H で現状を押さえる

**目的は現状把握そのもの。** 層別キーを洗い出すための道具ではない。
層別キーは別に選ぶ（`20_factor-axes.md` 第9章）。

| | 問い | 押さえること |
|---|---|---|
| When | いつ | 発生時期、時間帯、工程のどの時点 |
| Where | どこで | 工程、設備、製品のどの部位 |
| Who | 誰が | 担当者、班、経験年数 |
| What | 何が | 不良モード、現象 |
| **Which** | どれが | **どの機種・ロット・号機に出るか。出ないものは何か** |
| How much | どれだけ | 件数、率、損失額。**母数を必ず添える** |

**Why（なぜ）は入れない。** なぜを問うのは要因解析（ステップ5）の仕事で、
現状把握の段階で原因を推測すると、以降の分析がその仮説に引きずられる。
代わりに **Which** を残す。「出るもの／出ないもの」の対比が、後の層別の出発点になる。

**表に文章を書かない。1行1切り口に割る。** 「午後に多く、特に2号機で新人が担当した
ときに発生」は3つの事実が混ざっている。When・Which・Who に分けて書く。

**ここで層別を尽くしておくと、要因解析が劇的に楽になる。** 層別で差が出れば、それ自体が原因の手がかりになる。

### ステップ3：目標設定

- 「何を・いつまでに・どれだけ」を定量で書く
- 現状把握の数字を起点にする（現状0.8% → 目標0.3%、6月末まで）
- 道具：グラフ、マトリックス図

**部分の削減件数と、全体の率の改善が計算で一致すること。**
「対象2項目 40件→12件」と「全体 1.8%→0.68%」が式でつながっているかを必ず確認する。

```
現状の全体率 = 全体の不良件数 ÷ 母数
目標の全体率 = (全体の不良件数 − 対象項目の削減件数) ÷ 母数
```

つながらない場合は、目標値か削減件数のどちらかが根拠なく置かれている。

**対象外にする部分を明示する。** 「乾燥条件・その他の5件は今回は触らない」と書く。
書かないと、全体率の目標が達成不能な水準に置かれていても気づけない。

**ゼロを目標にしない理由を数字で示せるようにする。**
対象項目を全部なくしても到達しない水準がある。

```
対象項目を全て0にしたときの全体率 = (全体件数 − 対象項目件数) ÷ 母数
  → この値が今回の活動で到達しうる下限
```

この下限より低い目標は、対策が全部成功しても達成できない。
その場合は対象項目を追加するか、目標を見直す。検算の詳細は `90_handoff.md` 第7章。

### ステップ4：活動計画

- 誰が・何を・いつまでに
- 中間マイルストーンを置く
- 道具：**依存関係の有無で変わる**（下記）

**道具の選定は `00_mapping.md` 第5章 ステップ4 で引く。**
依存関係があればアローダイアグラム、なければガントチャートか表。
判断の理由は `40_n7.md` アローダイアグラム法。

#### 計画の順序で必ず確認すること

| 確認 | 理由 |
|---|---|
| **試行はテスト機・テストラインで行う** | 本番ラインの全面停止は現実的でない。試行のために生産を止める計画は承認されない |
| **対策が決まってから治具・設備を手配する** | 順序が逆。対策が変われば手配が無駄になる |
| 効果確認に必要な期間を計画に入れる | 対策後すぐには判定できない。母数が揃う期間が要る |
| 標準化（ステップ8）を計画に入れる | 飛ばされるのはたいていここ |

### ステップ5：要因解析

- 要因を洗い出し、絞り込み、データで検証する
- **発生原因**（なぜ作られたか）と**流出原因**（なぜ止められなかったか）の両方を見る
- 道具：特性要因図（大骨＝4M）、連関図、散布図、層別、なぜなぜ分析

**最大の落とし穴は、要因を挙げただけで真因と決めつけること。** 挙げた要因は仮説であり、必ずデータで確かめる。

### ステップ6：対策立案・実施

- 真因に対する対策を立て、実行する
- 応急処置と恒久対策を区別する
- 道具：系統図、マトリックス図、PDPC、ECRS、5E

### ステップ7：効果確認

- 対策前後を同じ指標・同じ層別で比較する
- 目標に届かなければステップ5に戻る
- 道具：**テーマの種類で変わる**（下記）

**道具はテーマの種類で変わる。** 分岐表は `00_mapping.md` 第5章 ステップ7 で引く。
件数を減らすテーマならパレート図の前後比較、ばらつきならヒストグラム・管理図。

前後比較では、**分類・期間長・縦軸の目盛りを揃える。**
目盛りが違うと、縮んだ分が改善効果として目に見えない（`30_qc7.md` パレート図の作図の仕様）。

**目標未達でも、達成度に応じた評価はできる。** 失敗として打ち切らず、どこまで効いたかを見る。

### ステップ8：歯止め（標準化）

- 効いた対策を作業標準書・QC工程表に反映する
- 関係者に教育する
- 道具：QC工程表、作業標準書、4M変更管理

**このステップを飛ばすと必ず再発する。** 改善活動が失敗する最大の原因。

## 3. 施策実行型

原因がすでに分かっている場合。**問題解決型からステップ5（要因解析）を省略する。**

```
テーマ選定 → 現状把握 → 目標設定 → 活動計画 → 対策実施 → 効果確認 → 標準化
```

### 使いどころ

- 原因が明白（設備の劣化、手順書の不備など）
- 緊急度が高く、要因解析に時間をかけられない

### 注意

**「原因は分かっている」という思い込みで施策実行型を選ぶと、対策が空振りする。**
根拠を確認する。データで裏付けがなければ問題解決型に戻す。

## 4. 課題達成型

現状の延長ではなく、より高い水準を目指す場合。現状把握・要因解析の代わりに**方策立案**が中心になる。

```
テーマ選定 → 攻め所と目標の設定 → 方策の立案 → 成功シナリオの追究
 → 実施 → 効果確認 → 標準化
```

| ステップ | 内容 | 道具 |
|---|---|---|
| 攻め所と目標 | どこを攻めれば目標に届くかを決める | マトリックス図、親和図 |
| 方策の立案 | 目標達成の手段を広く出す | 系統図 |
| 成功シナリオの追究 | 各方策の障害を予測し、対処を織り込む | PDPC、マトリックス図 |

**問題解決型との違いは「原因」ではなく「手段」を掘ること。**
問題がないところに原因を探しても何も出てこない。

## 5. 未然防止型

まだ起きていない問題に備える。**データがないのが前提**なので、言語データの道具が中心になる。

```
想定される問題の洗い出し → 重要度の評価 → 対策立案 → 歯止め
```

| ステップ | 内容 | 道具 |
|---|---|---|
| 洗い出し | 起こりうる不具合を挙げる | 特性要因図、連関図、4M × 3H |
| 評価 | 影響度・発生頻度・検出しやすさで優先順位を付ける | マトリックス図 |
| 対策 | 予防策と、起きた場合の対処を決める | 系統図、PDPC、5E |
| 歯止め | QC工程表・変更管理に組み込む | QC工程表、4M変更管理 |

**4M × 3H が最も有効な軸。** 「初めて・変更・久しぶり」は、まさに問題が起きる直前の状態を指す。

より体系的な手法（FMEA・FTA・DRBFM）はこのスキルの範囲外。必要なら利用者にその旨を伝える。

## 6. 型は複合する

**1つの案件が1つの型にきれいに収まることは、実務ではほとんどない。**
型は排他の選択肢ではなく、主たる骨格を1つ決めたうえで、必要な部分を他の型から借りる。

### 基本の考え方

```
主たる型を1つ決める
   │
   ├─ 骨格（ステップの並び）はこの型に従う
   └─ 個別のステップで、他の型のやり方を借りる
```

利用者には**主たる型だけを伝える。** 「問題解決型と課題達成型の複合で進めます」と
言われても現場は動けない。「問題解決型で進めます。ただし対策立案は課題達成型の
方策立案の考え方を使います」と、借りる箇所を具体的に示す。

**複合したときの道具の受け渡しは `90_handoff.md` 第1章。**
借りたステップは借りた型の行を引く。借りた箇所の前後が新しい継ぎ目になり、
ここで出所の違うものを1枚にまとめる失敗が最も多い。

### よくある複合パターン

| 状況 | 主たる型 | 借りる型 | 借りる箇所 |
|---|---|---|---|
| 復帰と引き上げを同時に求められた | 問題解決型 | 課題達成型 | 目標設定（復帰後の水準を上乗せ） |
| 原因が一部だけ分かっている | 問題解決型 | 施策実行型 | 既知部分は要因解析を飛ばして先行着手 |
| 対策が効かず再発した | 問題解決型 | 未然防止型 | 標準化（次の変化点を先に潰す） |
| 新工程だが類似工程の実績がある | 未然防止型 | 問題解決型 | 現状把握（類似工程のデータを流用） |
| 対策の実行段階で新たな不良が出た | 施策実行型 | 問題解決型 | 新規事象だけ要因解析を挿入 |

### 段階に分けるべき場合

複合ではなく**順番に分ける**方がよいケースがある。判断基準は、
**片方を達成しないともう片方に着手できないかどうか。**

典型は「復帰と引き上げ」。

```
第1段階  問題解決型で悪化分を潰し、元の水準に戻す
   ↓
第2段階  戻った水準を起点に、課題達成型で引き上げる
```

課題達成型には要因解析のステップがないため、**悪化分は課題達成型では拾えない。**
同時にやろうとすると、悪化の原因が残ったまま高い目標を追うことになる。

段階と段階の間そのものが継ぎ目になる。**第2段階の起点は、第1段階の目標値ではなく
実績値。** 管理線も第1段階の対策後データで引き直してから渡す（`90_handoff.md` 第1章）。

### 型が途中で変わる合図

進行中に以下が起きたら、型の見直しを検討する。

| 合図 | 疑うこと | 対応 |
|---|---|---|
| 「原因は分かっている」はずが対策が空振り | 施策実行型の前提が誤り | 問題解決型に戻して要因解析 |
| 要因解析で真因に届かない | データ不足、または課題達成型が適切 | 現状把握に戻る／型を見直す |
| 対策後に別の不良が出た | 副作用。新規事象 | その事象だけ問題解決型を挿入 |
| 効果確認で目標未達 | 真因の取り違え | ステップ5に戻る |

**型を変えたら、その旨を利用者に伝える。** 黙って変えると活動の記録が辻褄の合わない
ものになる。

## 7. 実務用と教材用で進め方が変わる

**同じ組み立て手順でも、何のために作るかで対象の絞り方と道具の数が変わる。**
用途は `SKILL.md` の Step 0.5 で判定する。**既定は実務用。**

| | 実務用（既定） | 教材用 |
|---|---|---|
| 目的 | 問題を実際に解く | 手順と道具の使い方を教える |
| 対象項目 | **1つに絞る**（重点指向） | 目標に必要な数だけ。複数なら**理由を書く** |
| ステップ | 必要なものだけ。**飛ばした理由を書く** | **組んだステップを最後まで通す** |
| 道具 | そのステップで要るものだけ。使わない選択もある | 各ステップで**何の判断を出すための道具か**を書く |
| 数値 | 実データ | 実データ、または架空の事例。**架空なら架空と明示し、数値骨格を先に固定する** |
| 分量 | 判断に要る分だけ | 各ステップ1〜2枚 |

### 実務用が既定である理由

**実務は重点指向で1項目に絞るのが主流。** 対策の資源が限られるため、
効果の大きい1項目に集中する方が成果が出る。

**複数項目を追うなら、その理由を明示する。**
「累積80%の2項目が必要」と言いながら以降1項目しか追わないのは矛盾で、
指摘を受ける。目標に必要な項目数を計算で出し（`90_handoff.md` 第6章）、
出た数だけ最後まで追う。

### 教材用で気をつけること

- **道具を使うこと自体が目的にならないようにする。** 各ステップで
  「この道具で何の数値・何の判断が決まるか」を書く。書けない道具は載せない
- **選ばなかった道具とその理由は資料に載せない。** 聞き手が知りたいのは
  目的を達成するためにどうするかであって、道具の選定経緯ではない
- **現実の案件で使われない道具を、教材だからと無理に入れない。**
  依存関係のない計画にアローダイアグラムを描く、件数を減らすテーマに管理図を描く、など

### 架空の事例を作るとき

**架空の事例は、推測で原因と対策を書くと必ず非現実的になる。** 次の順で作る。

| 順 | やること | 失敗例 |
|---|---|---|
| 1 | **数値骨格を先に固定する。** 全体件数・母数・項目別件数・目標・項目別の削減を決め、検算する（`90_handoff.md` 第9章） | 各スライドを作りながら数値を決め、途中で3回組み直す |
| 2 | **原因と対策を、その工程の一般的な不良事例に当たって確かめる。** 業界団体・部品メーカー・工具メーカーの技術資料など。確かめた出所を控える | 調べずに書いた原因が、その工程では起きない |
| 3 | **発生の仕組みと管理の不備を分ける。** 書き分け方は `30_qc7.md` 特性要因図「作図の仕様」 | 「校正周期が長い」を不良の発生の仕組みとして特性要因図に書く |
| 4 | **対策は、その工程で現実に取れる範囲から出す。** 設備投資を伴う対策は、実現性とコストの評価で落ちることを前提に並べる | 小さな不良に対して設備の増設を主対策にする |
| 5 | **架空であることを資料に明示する** | 実データのように見せる |

## 8. PDCA と SDCA

| サイクル | 用途 | 回す場面 |
|---|---|---|
| PDCA | 改善する | QCストーリーのステップ1〜7 |
| SDCA | 標準を守り、維持する | ステップ8以降の日常管理 |

改善で得た成果は SDCA に引き渡して維持する。**PDCAだけを回し続けると、成果が定着せず元に戻る。**

```
Standardize（標準化）→ Do（実行）→ Check（検証）→ Action（改善）
```

異常が出たら、まず標準どおりに作業されていたかを確認する。
守られていたのに異常が出たなら、標準そのものを見直す。

## 9. よくある失敗

| 失敗 | 症状 | 対処 |
|---|---|---|
| テーマが抽象的 | 現状把握で何を測ればいいか分からなくなる | 工程・不良項目まで絞る |
| データなしで原因を推測 | 対策が空振りする | 現状把握に戻り、必要ならチェックシートから作る |
| 要因＝真因と決めつけ | 対策後も改善しない | 層別・散布図で検証する |
| 流出原因を見ない | 同じ不良が客先に流れ続ける | 発生原因と流出原因を分けて追究する |
| 標準化しない | 数ヶ月後に再発する | ステップ8を必ず実施する |
| 型の取り違え | 活動が途中で停滞する | 第1章の3問に戻る |
| 型を厳格に守りすぎる | 実態に合わず形骸化する | 第6章。主たる型＋借用で組む |
| 複合を利用者にそのまま伝える | 現場が動けない | 主たる型を1つ伝え、借用箇所だけ具体的に示す |
| 目標の率と件数が式でつながらない | 対策が全部成功しても未達になる | ステップ3の検算を行う |
| 対策が評価なしに採用された | 絞り込みが1回しかない | `90_handoff.md` 第3章 |
| 道具は正しいが成果物が破綻している | ステップ間の受け渡しを誤った | `90_handoff.md` 第8章の症状表で切れ目を特定する |

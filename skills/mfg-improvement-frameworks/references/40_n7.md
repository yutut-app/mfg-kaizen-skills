# 40_n7 — 新QC7つ道具（言語データ）

**言語データを扱う道具。** 意見や知識を出し、整理して構造にするのに使う。
QCストーリーの 1 テーマ選定 / 4 活動計画 / 5 要因解析（前半）/ 6 対策立案 で使う。

カードを出す作業（ブレーンストーミング）は、これらの道具の**手順の一部**。
出す（発散）と整理する（収束）の両方が、1つの道具の中で起きる。

数値で絞り込み検証するのは `30_qc7.md`。**言葉で構造を作り、数値で確かめる**という
往復で使う（`00_mapping.md` 第2章）。

**データがない案件ではこちらが主役になる。**

**道具の出力を次の道具に渡すときは `90_handoff.md` を読む。** 継ぎ目の変換規則はそこにある。
特に 特性要因図 → 系統図 → マトリックス図 の3連結は、最も間違いが起きる箇所。

全ての道具を同じ8項目で記述している。**比較して選ぶための構成。**

## 親和図法

**ひとことで**：バラバラの言語データを、似たもの同士でまとめて構造を見つける。KJ法に由来する。

**こう言われたら使う**
> 「意見がバラバラで論点が見えない」「報告が多すぎてどこから手を付ければいいか分からない」
> 「アンケートの自由記述をどうまとめればいいか」

**こういうときは使わない**
- 分類がすでに適切に付いている → パレート図で件数を見る方が速い
- カードが10枚未満 → グループ化する意味が薄い

**必要なもの**：言語データ（意見・報告・気づき）。1件1枚のカードにする。

**分かること**：自分たちが気づいていなかった論点の構造。

**手順**
1. 事実・意見を1枚1件でカードに書き出す（ここがブレーンストーミング）
2. 似ていると感じるもの同士を集める
3. 集まったグループに見出しを付ける
4. グループ同士の関係を配置で表す

**実務での見極め**
- **分類軸を先に決めてはいけない。** 決めた瞬間にただの仕分けになり、新しい構造が見えない。「なんとなく似ている」で集めてから見出しを付ける
- **「不注意」「確認不足」のような結論めいた言葉が多数を占めていたら、この道具の出番**。もとの記述に戻ると、もっと具体的な状況が書かれている（`70_cases.md` ケース2）
- **件数の多寡で切り捨てない。** 少数意見に対策しやすい真因があることが多い

**よくある失敗**

| 症状 | 原因 | 対処 |
|---|---|---|
| 結局いつもの分類になった | 分類軸を先に決めた | カードから始め直す |
| グループの見出しが抽象的 | もとの記述に戻っていない | カードの言葉を使う |
| 1人でやって現場感がない | 文脈が抜けた | 報告した本人を入れる |

## 連関図法

**ひとことで**：要因を矢印でつなぎ、影響の大きいものを見つける。

**こう言われたら使う**
> 「原因が絡み合っていて整理できない」「対策してもまた別のところで問題が出る」
> 「特性要因図を描いたが、同じ要因が複数の大骨に出てくる」

**こういうときは使わない**
- 要因が階層で整理できる → 特性要因図の方が読みやすい
- 単一の変化点が起点になっている → 4M × 3H で足りる（`70_cases.md` ケース4）
- 要因が想定の域を出ない（未経験の工程）→ 精度が上がらない

**必要なもの**：言語データ。初期カードは4Mの各観点から出す。

**分かること**：影響の大きい要因（真因の候補）。

**手順**
1. 中央に問題を置く
2. 要因を書き出す
3. 「AがBを引き起こす」関係を矢印でつなぐ
4. 矢印の出入りを数える

**実務での見極め**
- **矢印が多く出ている要因＝影響が大きい**（対策の候補）
- **矢印が多く入っている要因＝結果に近い**（症状であって原因ではない）
- 特性要因図との使い分け：**階層なら特性要因図、循環なら連関図**。迷ったら特性要因図を先に描き、うまく分類できなければ切り替える

**よくある失敗**

| 症状 | 原因 | 対処 |
|---|---|---|
| 矢印だらけで読めない | 要因を絞っていない | 主要なものに限定する |
| 症状に対策してしまった | 矢印の向きを見ていない | 出ている矢印の多い方を選ぶ |

## 系統図法

**ひとことで**：目的を達成する手段を、階層的に枝分かれさせて展開する。**対策立案の中心。**

**こう言われたら使う**
> 「対策の案を出したい」「打ち手が思いつかない」「いつも同じ対策しか出てこない」

**こういうときは使わない**
- 対策が1つに決まっている → 展開する意味がない
- 目的が曖昧 → 先に現状把握へ戻る

**必要なもの**：達成したい目的（1つに絞られていること）と、**データで残した末端の真因**。

**分かること**：実行可能なレベルまで具体化された対策案の一覧。

**手順**
1. 左端に目的を置く。**目的はステップ3の目標**（特性の裏返し ＋ 数値 ＋ 期限）
2. **1次手段に、直前のステップで残ったものを裏返して動詞化したものを置く**
   （問題解決型＝末端の真因、施策実行型＝既知の原因、未然防止型＝残った想定問題。
   **課題達成型だけは裏返さず、攻め所を達成する方策として展開する**）
3. 各項目をさらに手段へ展開する（3〜4段）
4. 末端が実行可能になるまで続ける
5. **末端の案を全件、マトリックス図で評価する**

### 前の道具からの受け渡し

**特性要因図の階層は系統図の階層に対応しない。**

- 大骨（4M）は持ち込まない。4Mは分類の切り口であって手段ではない
- 要因は名詞・状態、手段は動詞・行動。裏返して動詞化し、**元の語を残す**
  （「ノズルに塗料が固着する」→「ノズルに塗料を固着させない」。「塗装設備を保全する」では追跡が切れる）
- **データで否定した要因には展開しない。** 展開すると、否定したはずの要因への対策が
  一覧に混ざり、ステップ5の絞り込みが無意味になる
  （出典：日科技連「新QC七つ道具の活用ポイント 第4回」）

変換規則の全体は `90_handoff.md` 第2章。

**実務での見極め**
- **1段目の展開に5Eを使うと視野が広がる**（教育・技術・強化・模範・環境）
- **教育に偏りやすい。** 「教育を徹底する」だけの対策は担当者が変われば消える。仕組みで防ぐ案（Engineering）を必ず含める
- 末端が「徹底する」「注意する」で終わっていたら展開不足
- 1次手段が否定形（「〜させない」）で止まるのは正しい。具体的な打ち手は2次以降で出す

**よくある失敗**

| 症状 | 原因 | 対処 |
|---|---|---|
| 末端が精神論 | 展開が浅い | もう1〜2段掘る |
| 対策が全部教育 | 5Eを使っていない | 技術・環境の観点を足す |
| 1次手段が「Man」「Machine」 | 大骨を持ち込んだ | 直前のステップで残ったものを裏返す |
| 課題達成型なのに真因を探している | 型と出力物の取り違え | 攻め所から方策を展開する |
| 手段が名詞で書かれている | 動詞化していない | 行動として書き直す |
| 否定した要因への対策が混ざる | 絞り込み前の要因を展開した | 残った要因だけに展開し直す |

## マトリックス図法

**ひとことで**：行と列に要素を置き、交点で関係の有無や強さを見る。

**こう言われたら使う**
> 「どの案を選べばいいか」「優先順位を付けたい」「要因と不良の対応を整理したい」

**こういうときは使わない**
- 選択肢が2つ以下 → 直接比較で足りる
- 評価軸が決まっていない → 先に軸を決める

**必要なもの**：比較したい要素と、評価軸。

**分かること**：優先順位。**評価軸の置き方で結論が変わる。**

**手順**
1. 行に評価対象、列に評価軸を置く
2. 交点に ◎○△ で評価する
3. 優先順位を出し、採否を決める

### 評価対象は系統図の対策案すべて

**「主要因への対策だから評価不要」は誤り。** 系統図の末端に並んだ案は全件が評価対象。
主要因に対する対策であっても、効果・実現性・コストは案ごとに違う。

| 系統図の出力 | マトリックス図での扱い |
|---|---|
| 末端の対策案 | 行に置く。**全件** |
| 途中の中間手段 | 行に置かない（そのままでは実行できないため） |

絞り込みが2回あること（要因をデータで絞る／手段を評価軸で絞る）は `90_handoff.md` 第3章。

### 評点法：セルは記号、総合は点数

**評価セルと総合列で書き方が違う。** ここを混ぜると、絞れない表になる。

| 列 | 書き方 | 理由 |
|---|---|---|
| 各評価セル | **記号（◎○△）** | 一覧したときに視覚で強弱が読める。数字を並べると図として読めない |
| 記号の対応点数 | **凡例に明示する**（◎3／○2／△1） | 記号だけでは総合が計算できない |
| 総合列 | **点数（合計）** | 順位が一意に決まる。記号のままでは並べ替えられない |
| 採否列 | **しきい値で機械的に決める** | 恣意的な採用を防ぐ |

```
凡例  ◎ 3点（大きい）   ○ 2点（ある）   △ 1点（小さい・条件つき）
採否  合計 10点以上を採用
```

**しきい値は先に決める。** 点数を出してから決めると、採りたい案が通る値に寄る。
評価軸が4つ（効果／実現性／コスト／副作用）なら満点12点、しきい値10点が目安。

### 絞れていない表は作り直す

**8案中6案採用は、絞ったことにならない。**
マトリックス図は絞るための道具で、通すための道具ではない。

| 採用率 | 判断 |
|---|---|
| 半分以上が採用 | **軸が甘い。** 相対評価にするか、しきい値を上げる |
| 3分の1程度 | 妥当 |
| 1案のみ | 展開不足の疑い。系統図に戻る |

不採用にした案と理由も残す（`90_handoff.md` 第4章）。

**実務での見極め**
- 対策選定の評価軸：効果／実現性／コスト／副作用
- **QCDを評価軸にするとトレードオフが見える。** 効果だけで選ぶとコストや納期を圧迫する案に偏る
- 未然防止では「**気づけるか**（検出しやすさ）」を軸に加える。発生頻度が低くても気づけない不具合は客先に流れる（`70_cases.md` ケース5）

**よくある失敗**

| 症状 | 原因 | 対処 |
|---|---|---|
| 全部◎になる | 軸が甘い | 相対評価にする |
| 選んだ案が実行されない | 実現性を見ていない | 軸に加える |
| 評価表がなく案が即採用された | 2回目の絞り込みを飛ばした | 系統図の末端を全件評価する |
| 総合列が記号のままで順位が付かない | 総合を点数にしていない | 凡例（◎3／○2／△1）を置き、合計を出す |
| 各セルが数字で図として読めない | セルを点数で書いた | セルは記号に戻す。点数は凡例と総合列だけ |
| 8案中6案が採用された | しきい値が甘い | 軸を相対評価にするか、しきい値を上げる |

## アローダイアグラム法

**ひとことで**：作業の順序と所要時間を矢印でつなぎ、全体日程と最長経路を見る。

**こう言われたら使う**
> 「スケジュールを引きたい」「どこがボトルネックか知りたい」「並行して進められる作業は」

**こういうときは使わない**
- **作業に依存関係がない**（すべて並行して進められる）→ **使わない。** ガントチャートか表で足りる
- 依存関係が単純 → ガントチャートで足りる
- 作業が5つ以下 → 描く手間に見合わない

### 依存関係があるときだけ使う

**アローダイアグラムの価値はクリティカルパスを出すことにある。**
依存関係がなければクリティカルパスは存在せず、描いても何も分からない。
「活動計画のステップだから」という理由で使わない。

| 作業の関係 | 使う道具 |
|---|---|
| Aが終わらないとBに入れない（依存あり） | アローダイアグラム |
| 並行して進められる（依存なし） | **ガントチャート**（担当と期間の割付） |
| 作業が5つ以下 | 表（担当・期限・成果物） |

**ガントチャートはQC7つ道具にも新QC7つ道具にも含まれない。**
使ってよいが、「7つ道具を使った」とは書かない。

**必要なもの**：作業の一覧、前後関係、所要時間。

**分かること**：全体日程と、遅れが全体に響く経路（クリティカルパス）。

**手順**
1. 作業を洗い出す
2. 前後関係を決める
3. 所要時間を見積もる
4. 矢印でつなぎ、最長経路を求める

**実務での見極め**
- **クリティカルパス上の作業に資源を優先配分する。** ここが遅れると全体が遅れる
- クリティカルパス上にない作業は、多少遅れても影響がない

**よくある失敗**：所要時間の見積もりが楽観的すぎて、計画が最初から破綻する。

## PDPC法

**ひとことで**：計画が思いどおりに進まない場合に備え、分岐と迂回路をあらかじめ描く。

**こう言われたら使う**
> 「対策がうまくいかない場合に備えたい」「初めてやるので何が起きるか読めない」
> 「トラブルを事前に潰しておきたい」

**こういうときは使わない**
- 手順が確立していて失敗の余地がない → 不要
- 失敗パターンを具体的に挙げられない → 挙げられるまで情報を集める

**必要なもの**：出発点、目標、想定される手順。

**分かること**：どのルートを通っても目標に到達できるか。

**手順**
1. 出発点と目標を置く
2. 想定される手順を並べる
3. 各段階で「うまくいかない場合」を想定する
4. その場合の代替ルートを描く
5. 全ルートが目標に到達するか確認する

**実務での見極め**
- **「うまくいく前提」の計画しか描けていないなら、この道具を使う意味がない。** 失敗パターンを具体的に挙げることが本体
- 未然防止型では本領を発揮する。想定外は必ず起きるため（`70_cases.md` ケース5）

**よくある失敗**：分岐が「失敗したらやり直す」だけになる。具体的な代替手段を書く。

## マトリックスデータ解析法

**ひとことで**：多変量の数値データを、主成分分析などで少数の軸に要約する。
**新QC7で唯一、数値を扱う。**

**こう言われたら使う**
> 「品質特性が多すぎて全体像が見えない」「官能評価の項目が多くてまとめられない」

**こういうときは使わない**
- 項目が少ない → 散布図やマトリックス図で足りる
- **統計処理の環境や知識がない** → 他の道具を提案する

**必要なもの**：多変量の数値データ。

**分かること**：データ全体の構造、項目間の関係。

**手順**：専用の統計処理が必要。

**実務での見極め**：**他の6つに比べて実務での使用頻度は低い。**
利用者から明示的に求められた場合のみ扱い、それ以外は他の道具を提案する。

**よくある失敗**：結果の解釈が難しく、現場に説明できない。説明できない分析は使われない。

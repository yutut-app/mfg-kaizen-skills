# 30_qc7 — QC7つ道具（数値データ）

**数値データを扱う道具。** 事実を確かめ、絞り込むのに使う。
QCストーリーの 2 現状把握 / 5 要因解析（後半）/ 7 効果確認 / 8 歯止め で使う。

言語データを構造にするのは `40_n7.md`。**言葉で構造を作り、数値で確かめる**という
往復で使う（`00_mapping.md` 第2章）。

**道具の出力を次の道具に渡すときは `90_handoff.md` を読む。** 継ぎ目の変換規則はそこにある。

全ての道具を同じ8項目で記述している。**比較して選ぶための構成。**

## パレート図

**ひとことで**：項目別の件数を大きい順に並べ、どこに集中しているかを見る。

**こう言われたら使う**
> 「どこから手を付ければいいか分からない」「不良の種類が多すぎる」「対策が効いたか見たい」

**こういうときは使わない**
- 分類が結論になっている（「不注意」「確認不足」）→ 先に親和図で分類し直す（`70_cases.md` ケース2）
- 対象がすでに1項目に絞れている → 描く意味がない
- 項目が3つ以下 → 棒グラフで足りる

**必要なもの**：項目別の件数または金額。50件以上。

**分かること**：重点対象。累積70〜80%までの項目に絞れる。

**手順**
1. 分類項目を決める（不良の種類・工程・原因）
2. 件数または金額を集計し、降順に並べる
3. 棒グラフ＋累積比率の折れ線を描く
4. **目標から逆算して、重点対象とする項目数を決める**（下記）

### テーマにする項目数は目標から逆算する

**テーマは上位1項目とは限らない。** 「上位1項目」と先に決めてから目標を置くのではなく、
**目標に届くかで項目数を決める。**

```
目標値を置く
   ↓
上位1項目を全部なくしたら目標に届くか（式で検算する）
   ├─ 届く  → テーマは上位1項目
   └─ 届かない → 2番目を足す。それでも届かなければ3番目
```

届かないまま上位1項目に絞ると、**対策が全部成功しても目標未達**になる。
検算の式は `90_handoff.md` 第7章。累積70〜80%は目安であって、目標との検算がこれに優先する。

### 二段階で使う

1段目で不良項目を選び、**2段目でその項目の中身を層別してさらに絞る。**

```
1段目：不良項目別   → 「寸法不良」が最大
2段目：寸法不良を層別（号機別・時間帯別・機種別）→ 2号機の段取り直後に集中
テーマ：2号機の段取り直後の寸法不良を減らす
```

1段目で止めると、テーマが「寸法不良を減らす」のままになり、
以降のステップで何を測ればよいかが決まらない。

### 作図の仕様

**簡易な図を描かない。** 以下を満たさない図はパレート図として成立していない。
実装は `assets/plot_pareto.py` を使う。**自分で軸を組み立てない。**

| # | 仕様 | 満たさないと何が起きるか |
|---|---|---|
| 1 | **累積折れ線の起点を原点（0）から引く。** 1本目の棒の左端・高さ0が始点 | 最初の項目の寄与が読めず、累積の意味が崩れる |
| 2 | **左軸（件数）の最大値と右軸（累積比率100%）を対応させる。** 左軸の最大＝総件数、そこに右軸の100%を合わせる | 折れ線と棒の高さが対応せず、目視で累積が追えない |
| 3 | **棒と棒の隙間をなくす**（`width=1.0`、枠線で区切る） | 棒グラフに見え、パレート図と区別できない |
| 4 | **件数の合計が右軸の100%と一致する。** 「その他」を含めて合計する | 累積比率が100%に届かず、検算できない |
| 5 | **累積80%が何件目・何件かを図中に注記する**（補助線と数値ラベル） | 線だけでは何項目が対象か直感で分からない |
| 6 | **前後比較では左軸の目盛りを両方そろえる。** 対策前の最大値に合わせる | 縮んだ分が改善効果として目に見えない。別々に描くと改善が消える |

仕様2と4はセット。**総件数を左軸の最大に置けば、右軸100%と自動的に一致する。**

**前後比較は必ず横並びで、同じ縦軸目盛りにする。** これが効果確認の主役
（`00_mapping.md` 第5章 ステップ7）。

**実務での見極め**
- **件数で描くか金額で描くかで結論が変わる。** 損失額が問題なら金額で描く。「件数は少ないが1件あたりの損失が大きい」項目を取りこぼさない
- 「その他」が最大になったら**分類が不適切**。分類をやり直す
- 効果確認では**対策前と同じ分類・同じ期間長**で描く
- 件数の合計が元の総数と一致することを確認する

**よくある失敗**

| 症状 | 原因 | 対処 |
|---|---|---|
| 毎回同じ項目が1位で対策が効かない | 分類が抽象的 | 分類を具体化する。二段階目の層別に進む |
| 対策が全部成功しても目標に届かない | 項目数を目標から逆算していない | 項目を追加するか目標を見直す |
| テーマが「不良を減らす」のまま | 二段階目を描いていない | 層別して絞る |
| 前後比較で改善が見えない | 期間長が違う | 条件を揃える |

## 層別

**ひとことで**：データを条件で分けて、差が出るかを見る。

**こう言われたら使う**
> 「ばらつきが大きい」「原因を整理したい」「なぜか特定のときだけ不良が出る」

**こういうときは使わない**
- 層別キーが記録されていない → 後から付けられない。`60_data-design.md` へ
- 1水準あたり10件未満 → 差があっても偶然と区別できない

**必要なもの**：層別キーを持つデータ。

**分かること**：どの条件で差が出るか。**差が出たキーが原因の手がかりになる。**

**層別キーの定番**

**層別キー ≠ 4M。** 時間帯・場所は4Mのどれにも属さないが、層別キーとしては定番。
4Mを層別キーの一覧として使うと、この2つが最初から候補に入らない。

| 時間別 | 設備別 | 作業者別 | 材料別 | 方法別 | 場所別 |
|---|---|---|---|---|---|
| 日付、曜日、時間帯、シフト、段取り直後 | 号機、ライン、金型、治具 | 個人、班、経験年数 | ロット、仕入先、材料グレード | 加工条件、手順バージョン、機種 | 工場、工程位置、保管場所、部位 |

詳細は `20_factor-axes.md` 第9章。

**手順**
1. 上の6キーから候補を挙げる
2. キーごとにパレート図・ヒストグラム・管理図・散布図を描き分ける
3. **件数と母数を並べて**差の有無を確認する
4. 差が出たキーを掘り下げる

**層別表の作法**

| ルール | 理由 |
|---|---|
| **必ず母数を添える** | 件数だけでは判断できない。10件／100個 と 10件／10000個 は別の話 |
| **件数の合計・母数の合計が元の値と一致すること** | 一致しなければ分類漏れか重複がある。どのキーで割っても検算する |
| **件数・母数の欄に範囲表記（「11〜14件」）を使わない** | 合計が検算できず、上の一致確認ができなくなる。目安値や区間の説明は対象外 |

**実務での見極め**
- **層別は要因解析の最短経路。** 特性要因図で要因を挙げる前に、まず層別で差を見た方が早いことが多い（`70_cases.md` ケース1）
- **差が出なかったキーも記録する。** 「調べて差がなかった」は立派な成果で、次に同じ調査を繰り返さずに済む
- 全体では相関がなくても層別すると見える、逆に全体で見えた相関が層別で消える、どちらも起きる
- 層別で残した要因・落とした要因の記録の様式は `90_handoff.md` 第4章

**よくある失敗**

| 症状 | 原因 | 対処 |
|---|---|---|
| 層別したいのにできない | 記録時にキーを取っていない | 取得設計からやり直す |
| どの層でも差が出ない | キーの選び方が的外れ | 別のキーを試す。時間別・場所別を見落としていないか確認する |
| 率の比較が成立しない | 母数を書いていない | 件数と母数を並べて書き直す |
| 縦計が元の件数と合わない | 分類漏れ、重複、範囲表記 | 実数で書き直し、合計を検算する |

## ヒストグラム

**ひとことで**：測定値を区間ごとの度数で表し、分布の形を見る。

**こう言われたら使う**
> 「寸法がばらつく」「規格に対してどのくらい余裕があるか知りたい」

**こういうときは使わない**
- データが合否のみ（数値でない）→ ばらつきは見えない
- 30件未満 → 形が読めない
- 時間的な変化を知りたい → 管理図

**必要なもの**：測定値30件以上（望ましくは100件以上）。

**分かること**：中心の位置、ばらつきの幅、分布の形、規格との関係。

**手順**
1. データを集める
2. 区間数を決める（データ数の平方根が目安）
3. 度数を数えて柱状に描く
4. 規格上限・下限があれば線を引く

**実務での見極め**

| 形 | 疑うこと |
|---|---|
| 左右対称の山が1つ | 正常 |
| **山が2つ** | **異なる条件が混ざっている。層別する** |
| 片側に偏る | 選別・除去が行われている |
| 離れ小島 | 異常値・別ロットの混入 |
| 規格をはみ出す | 工程能力不足 |

- **二山を見たら反射的に層別する。** 最も再現性の高い判断
- **中心ずれとばらつき拡大は対策が真逆。** 中心ずれなら設定変更、ばらつき拡大なら要因追究。必ず判別する

**よくある失敗**

| 症状 | 原因 | 対処 |
|---|---|---|
| 形が読めない | 件数不足、区間数が不適切 | 件数を増やす、区間を調整 |
| 良品のデータがない | 不良品だけ集めた | 全数または抜取で取り直す |

## 管理図

**ひとことで**：時系列に中心線と管理限界線を引き、工程が安定しているかを見る。

**こう言われたら使う**
> 「工程が安定しているか知りたい」「異常を早く見つけたい」「対策後も維持できているか」

**こういうときは使わない**
- **テーマが件数・率の削減** → **使わない。** パレート図の前後比較を使う（下記）
- 群が20未満 → 管理限界が定まらない
- 時間の情報がない → 描けない

### 件数を減らすテーマには使わない

**管理図・Cp・Cpk は「ばらつきを判断する」道具。**
「クレーム件数を半減する」のようなテーマでは、見るべきは件数の減少であって
ばらつきの安定性ではない。持ち込んでも何も判断できず、資料が1枚無駄になる。

**テーマごとの分岐表は `00_mapping.md` 第5章 ステップ7。** ここには置かない。

**必要なもの**：時系列の測定値または計数値。20〜25群以上。

**分かること**：偶然のばらつきか、異常な原因があるか。

**種類の選び方**

| データの種類 | 使う管理図 |
|---|---|
| 測定値・群あり | X̄-R |
| 測定値・1点ずつ | X-Rs |
| 不良個数（サンプル数一定） | np |
| 不良率（サンプル数変動） | p |
| 欠点数（サンプル数一定） | c |
| 単位あたり欠点数 | u |

**手順**
1. データの種類から管理図の型を選ぶ
2. **中心線と管理限界線をデータから計算する**（下の式）
3. 打点し、判定ルールで異常を見る

### 管理線の計算式

**管理線は必ずデータから計算する。それらしい値を置かない。**
根拠なく置いた管理限界は、打点の大半が限界外に出るなどして必ず破綻する。

| 管理図 | CL（中心線） | UCL / LCL |
|---|---|---|
| p（不良率・n変動） | p̄ ＝ 総不良数 ÷ 総検査数 | p̄ ± 3√( p̄(1−p̄) ÷ n ) |
| np（不良個数・n一定） | n·p̄ | n·p̄ ± 3√( n·p̄(1−p̄) ) |
| c（欠点数・n一定） | c̄ | c̄ ± 3√c̄ |
| u（単位あたり欠点数） | ū | ū ± 3√( ū ÷ n ) |
| X̄-R | X̄ の平均、R̄ | X̄ ± A₂R̄ ／ R は D₄R̄・D₃R̄（係数表を使う） |

- **p管理図は n が群ごとに変わるため、管理限界線も群ごとに上下する。** 一本の直線にならない
- 計算した LCL が負になる場合は **LCL なし**とする（0 を下回る不良率は存在しない）
- **n が小さいと管理限界が広がりすぎて、何も検出できない。** 群の大きさを先に確認する

### 判定ルール

| ルール | 意味 |
|---|---|
| 管理限界の外に点が出る | 異常原因がある |
| **連続9点が中心線の片側**に並ぶ | 水準が動いた |
| 連続6点が上昇または下降し続ける | 傾向がある |
| 周期性がある | 周期的な要因（シフト、ロットなど）がある |

### 管理限界と規格限界は別物

| | 出どころ | 意味 |
|---|---|---|
| 管理限界（UCL/CL/LCL） | **データから計算する** | 工程が普段どうばらついているか |
| 規格限界（USL/LSL） | 要求値として与えられる | 顧客・設計が許す範囲 |

混同すると「規格内だから問題ない」と工程の異常を見逃す。**同じ図に引くなら線種を分ける。**

### 改善の確認で見るのは下側

**改善の確認で見るのは LCL（下側）。** 「不良率が下がった」ことを統計的に示すには、
打点が LCL を割ったか、または連続9点が中心線の下側に並んだかを見る。
上振れ検出の UCL はこの場面では主役ではない。

### 対策後は管理線を引き直す

効果確認が済んだら、**対策後のデータで CL・UCL・LCL を計算し直す。**
対策前の管理線のまま日常管理を続けると、改善後の水準では全点が下側に張り付き、
その後の異常を検出できなくなる。

**実務での見極め**
- 歯止めのステップでは、日常管理の道具として使い続ける
- 管理図と目標値の関係（部分と全体の整合）は `90_handoff.md` 第7章

**よくある失敗**

| 症状 | 原因 | 対処 |
|---|---|---|
| 管理限界を規格線として使っている | 概念の混同 | 別々に引く |
| 管理限界がそれらしい値で置かれている | データから計算していない | 上の式で計算し直す |
| 改善したのに管理図で示せない | UCL側だけ見ている | LCL と連続9点のルールで見る |
| 対策後に全点が下側に張り付く | 管理線を引き直していない | 対策後のデータで再計算する |
| 異常が出ても放置 | 処置ルールがない | QC工程表に異常時の処置を明記 |

## 散布図

**ひとことで**：2つの量を点で打ち、関係があるかを見る。

**こう言われたら使う**
> 「温度と不良に関係があるか確かめたい」「この条件を変えれば良くなるのか」

**こういうときは使わない**
- 片方が分類（号機・作業者）で量ではない → 層別を使う
- 30組未満 → 傾向が読めない

**必要なもの**：対になった数値30組以上。

**分かること**：2つの量の関係の有無と向き。**仮説の検証に使う。**

**手順**
1. 対になったデータを集める
2. 横軸に原因系、縦軸に結果系を取る
3. 点を打ち、傾向を見る
4. 必要なら層別して色分けする

### 作図の仕様

**点だけを打った散布図は読めない。** 以下を満たす。実装は `assets/plot_scatter.py` を使う
（1〜4を既定で描く。1を書かないとエラーで止まる）。

| # | 仕様 | 満たさないと何が起きるか |
|---|---|---|
| 1 | **何の値を決めるための散布図かを、図の前（表題）に書く** | 読み手が何を見ればよいか分からない。「それは何のためか」と聞かれる |
| 2 | **基準線を引く**（結果側の規格、原因側の設定の許容範囲など） | 点がどこにあれば問題なのかが読めない |
| 3 | **基準を外れる領域を塗り、何の領域かを書き込む** | 外れた点があるかを、線を目で追わないと判断できない |
| 4 | **群のラベルを点の近くに書く。** 凡例だけにしない | 凡例と点を目で往復しないと、どの点がどの群か分からない |
| 5 | 軸に量と単位を書く。相関係数と点の数を図中に書く | 何を何に対して打ったか、どれだけのデータかが分からない |

**実務での見極め**
- **相関があっても因果とは限らない。** 第三の要因が両方に影響していることがある
- 測定範囲が狭いと相関が見えない。条件を広げたデータが要る場合がある
- 要因解析の後半で、特性要因図で挙がった仮説を潰すのに使う

**よくある失敗**

| 症状 | 原因 | 対処 |
|---|---|---|
| 相関を因果と断定 | 検証不足 | 条件を変えて再現するか確認 |
| 点が団子になる | 範囲が狭い | 条件を広げて取り直す |
| 散布図が読めないと言われた | 目的・基準線・群の位置が図にない | 作図の仕様1〜4を満たす（`plot_scatter.py`） |

## チェックシート

**ひとことで**：データを記録する、または抜け漏れを防ぐための帳票。**7つ道具で唯一データを作る側。**

**こう言われたら使う**
> 「何を記録すればいいか分からない」「データがない」「点検の抜けを防ぎたい」

**こういうときは使わない**
- すでに十分なデータがある → 分析の道具へ進む

**必要なもの**：なし。**これから作る。**

**分かること**：後の分析に使えるデータそのもの。

**2種類**

| 種類 | 目的 |
|---|---|
| 記録用 | 現状把握のためにデータを取る |
| 点検用 | 確認の抜け漏れを防ぐ |

**手順**：設計の5項目（何を／どの単位で／誰が／いつ／層別キー）を先に決める。詳細は `60_data-design.md`。

**実務での見極め**
- **層別キーは記録時にしか取れない。** 迷ったら入れる
- **合否ではなく数値を記録する。** 合否だけではばらつきが見えない
- その場で書ける形式にする。後でまとめて書く運用は精度が落ちる

**よくある失敗**：`60_data-design.md` 第7章にまとめてある。

## 特性要因図

**ひとことで**：魚の骨の形で、結果に対する要因を階層的に洗い出す。**要因解析で使う道具。**

**こう言われたら使う**
> 「原因を整理したい」「何が影響しているか洗い出したい」

**こういうときは使わない**
- **層別できるデータがある** → 先に層別する方が速い（`70_cases.md` ケース1）
- **原因がすでに分かっている** → 施策実行型。洗い出しは不要（ケース4）
- 要因が相互に影響し合い循環している → 連関図（`40_n7.md`）
- 特性（結果）が1つに定まっていない → 親和図で整理が先（ケース2）

**必要なもの**：なし（言語データ）。ただし**現場の人の知識**が要る。

**分かること**：要因の網羅的なリスト。**これは仮説であって真因ではない。**

**手順**
1. 右端に解決すべき特性を置く（背骨）
   ※ 要因を出す作業はブレーンストーミングで行う。現場の人を必ず入れる
2. **大骨に4Mを置く**（安全なら安全工学の4M、環境が絡むなら5M＋1E）
3. 中骨・小骨へ掘り下げる。**線で枝分かれさせて描く**。箇条書きにしない
4. 疑わしい要因に印を付ける
5. **データで検証する**（層別・散布図）。残った末端の真因が次のステップの入力になる

### 作図の仕様：各階層に何を書くか

**呼称ではなく中身の定義。** ここが決まっていないと、何度描き直しても収束しない。
実装は `assets/plot_fishbone.py` を使う。

| 階層 | 何を書くか | 書き方 | 例 |
|---|---|---|---|
| 特性（背骨） | **解決すべき結果**。1つだけ | 名詞。数値があれば添える | 塗装ムラ（1.8%） |
| 大骨 | **分類の切り口**。4M など | 切り口の名前 | Man / Machine / Material / Method |
| 中骨 | **具体的な要因**。現場で起きている事象 | 名詞または状態 | ガンとワークの距離が一定しない |
| 小骨 | **中骨が起きる仕組み**。なぜそうなるか | 名詞または状態 | 距離を目測で合わせている |

**「知らない」「できない」「やらない」は型であって中骨ではない。**
これらは要因を洗い出すときの**発想の切り口**（作成者が頭の中で使うもの）で、
図に書くと何も指していない枝になる。「知らない」ではなく
「ガンとワークの距離を目測で合わせている」と、**事象で書く。**

| 図に書かないもの | 理由 | 代わりに書くもの |
|---|---|---|
| 4Mという語そのもの以外の型（知らない／できない、3H、5E） | 型は作成時の道具。読み手には不要 | 型から出てきた具体的な事象 |
| 「〜不足」「〜不十分」だけの語 | 何が起きているか分からない | 何がどう不足しているか |

**中骨・小骨には、まず発生の仕組みを書く。** 点検・校正の周期、清掃頻度、標準書の記載漏れ
のような管理の不備は、不良が「なぜ起きるか」ではなく「なぜ防げなかったか」の話になる。
発生の仕組みと同じ欄に混ぜない。混ぜると、対策が管理の強化（周期を短くする、点検を増やす）
に寄り、発生の仕組みそのものに手が入らない。

| 書く位置 | 例 |
|---|---|
| 中骨・小骨（発生の仕組み） | ノズルに塗料が固着する、距離を目測で合わせている |
| 発生の仕組みの下、または歯止め・流出原因の側 | ノズルの清掃間隔が決まっていない、校正の周期が長い |

管理の不備が本当に効いているなら、発生の仕組みを書いた後で「なぜその状態を防げなかったか」
として掘り下げる。**発生の仕組みを飛ばして管理の不備から書き始めない。**

**小骨の本数を大骨ごとに変えない。** Man に小骨が6本、Machine に1本という図は、
「Man が主要因だ」と読まれる。掘り方の差が結論に見えてしまう。
**均等に掘り、絞り込みはデータで行う**（`90_handoff.md` 第4章）。
掘れない大骨があるなら、その旨を図の外に注記する。

### 呼称は宣言してから使う

**大骨・中骨・小骨・孫骨は通称であり、JIS・日科技連の規格用語ではない。**
JIS Q 9024 では「主軸・大枝・小枝」と呼ぶ。

さらに「大骨＝1次要因」とするかは流派が割れる。
大骨は分類の切り口であって要因ではない、という立場もある。

| 呼び方 | 出どころ |
|---|---|
| 大骨・中骨・小骨 | 現場で広く使われる通称 |
| 主軸・大枝・小枝 | JIS Q 9024 |
| 1次要因・2次要因 | 流派により大骨から数えるか中骨から数えるかが割れる |

**社内で使うならどちらか宣言して固定する。** 混在させると、同じ資料の中で
「1次要因」が指すものが変わる。このスキルでは通称（大骨・中骨・小骨）を使い、
規格用語に触れる必要がある場面でのみ JIS の呼称を併記する。

**実務での見極め**
- **挙げただけでは仮説。** 必ずデータでの検証へ進む
- **図の中で真因を表示しない**（赤字・丸印・「真因」の書き込み）。この段階では全部が候補。確定は検証の後（`90_handoff.md` 第10章）
- 大骨の選び方は `20_factor-axes.md`
- 同じ要因が複数の大骨に出てくる、分類がうまくいかない → 連関図に切り替える合図
- 要因を想像して埋めない。現場の言葉を使う
- **絞り込みの単位は末端の要因。** 大骨ごと残す／落とすをしない。`90_handoff.md` 第4章
- **系統図への渡し方を必ず確認する。** 階層は対応しない。`90_handoff.md` 第2章

**よくある失敗**

| 症状 | 原因 | 対処 |
|---|---|---|
| 図は立派だが対策が決まらない | 検証していない | 層別・散布図で絞る |
| 要因が一般論ばかり | 現場の知識が入っていない | 現場と一緒に作る |
| 小骨が箇条書きで書かれている | 図にしていない | 線で枝分かれさせて描き直す |
| 系統図の1次手段に「Man」「Machine」が並んだ | 大骨を手段に持ち込んだ | `90_handoff.md` 第2章 |

## グラフ

**ひとことで**：大小・推移・割合を視覚化する。

**こう言われたら使う**：どのステップでも、数値を見せる必要があるとき。

**こういうときは使わない**：専用の道具がある場合（分布ならヒストグラム、安定性なら管理図）。

**必要なもの**：目的に応じた数値。

**分かること**：目的による。

| 種類 | 用途 |
|---|---|
| 棒グラフ | 大小の比較 |
| 折れ線グラフ | 時間的な推移 |
| 円グラフ・帯グラフ | 構成比 |
| レーダーチャート | 複数項目のバランス |

**手順**：目的を決める → 形式を選ぶ → 描く。

**実務での見極め**：目的と形式が合っているかを確認する。推移を円グラフで描くなどの誤用が多い。

**よくある失敗**：軸の起点を0にしないことで差を誇張してしまう。比較の場面では特に注意する。

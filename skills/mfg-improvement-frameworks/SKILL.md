# 製造業改善フレームワーク

製造現場の改善を、適切なフレームワークを選定しながら進める。

**このスキルの価値は「手法の解説」ではなく「選定と接続」にある。**
解説だけを返さない。常に「今どのステップにいて、次に何を作るか」を示す。

**前提を確定してから先へ進む。** 不良モードの定義、テーマ、対象範囲、目標。
ここが曖昧なまま進むと、以降のステップが全部ずれ、最後に作り直しになる。
確定できないときは、**次のステップに進まずに確定させる。**
似た不良モード（塗装の「ムラ」と「たれ」など）を1つのテーマに混ぜない。

## 組み立て手順（最上位）

**QCストーリーは順番固定の手順ではない。** ステップも道具も部品で、案件ごとに組む。
ステップの順番・回数・有無は案件で変わる（現状把握を2回行う、など）。
下の5段で組み、各段の中で「進め方」の Step 0〜5 を部品として使う。

| 段 | やること | 詳細 |
|---|---|---|
| 1 前提を固める | 不良モードの定義・テーマ・対象範囲・方針目標を確定する | `10_qc-story.md` ステップ1 |
| 2 決めたい判断を並べる | 各段で**何の数値・何の判断が決まれば先に進めるか**を書く | 下記 |
| 3 部品を選んで組む | 判断ごとにステップと道具を選ぶ。**道具はQC7・新QC7に限らない。分かりやすさを優先する** | `00_mapping.md` 第5章 |
| 4 数値骨格を固定する | 件数・母数・項目別の削減・目標を先に決めて検算してから、各資料に入る | `90_handoff.md` 第9章 |
| 5 見本の現実性を確かめる | 原因と対策を、その工程の一般的な不良事例に当たって確かめる | `10_qc-story.md` 第7章 |

**段2の書き方。** 道具の名前から書かない。決まる判断から書く。

- 悪い：「散布図を描く」
- 良い：「塗料の粘度と不良率に相関があるかを決める → 散布図」

段2が書けない道具は、使う理由がない。聞き手に「それは何のためか」と聞かれる。

## 進め方

**以下の Step 0〜5 は、組み立て手順の段3で使う部品。** 上から順に1回ずつ通すものではない。

### Step 0：入力形式を判定する（必ず行う）

| 入力 | 初動 |
|---|---|
| Excel / CSV | 読み込み、列構成・件数・層別キーの有無を確認する |
| 帳票・PDF | 抽出し、表として構造化できるか判定する |
| 口頭・手入力 | 言語データとして扱う |
| **データがない** | **数値の道具に進まない。** `60_data-design.md` を読み、取得設計を行う |

**推測値でグラフを作らない。** 件数が不足している場合も作図せず、その旨を伝える。

### Step 0.5：用途を判定する

**実務用か教材用かで、対象の絞り方と道具の数が変わる。** 型より先に決める。

| 用途 | 対象項目 | ステップ | 道具 |
|---|---|---|---|
| **実務用（既定）** | **1つに絞る**（重点指向） | 必要なものだけ。飛ばした理由を書く | 要るものだけ。使わない選択もある |
| 教材用 | 目標に必要な数だけ。複数なら理由を書く | **組んだステップを最後まで通す** | 各ステップで、何の判断を出すための道具かを書く |

**既定は実務用。** 教材・研修・勉強会と明示されたときだけ教材用にする。
差分は `10_qc-story.md` 第7章。

### Step 1：型を選ぶ

3問で決まる。詳細は `00_mapping.md` 第4章。

1. まだ起きていないリスクへの備えか → 未然防止型
2. 現状復帰ではなく、今より上の水準を目指すか → 課題達成型
3. 原因はすでに分かっているか → 施策実行型 / 分かっていない → 問題解決型

**選ぶのは「主たる型」1つ。排他ではない。** 1案件が1つの型に収まることは実務では
まれで、必要な部分は他の型から借りる。複合パターンは `10_qc-story.md` 第6章。

- 両方に当てはまるときは**問題解決型に倒す**
- 復帰と引き上げを同時に求められたら**段階に分ける**（復帰が先）
- **利用者には主たる型だけを伝える。** 「複合で進めます」では現場が動けない。
  借りる箇所だけを具体的に示す

### Step 2：今どのステップかを特定する

利用者に「今どこにいるか」を確認する。すでに現状把握が済んでいるのに、
テーマ選定からやり直させない。

### Step 2.5：データの種類で道具を選ぶ

**手元にあるデータの種類が、使える道具を決める。**

| 手元にあるもの | 使う道具 |
|---|---|
| 言語データ（意見・報告・現場の知識） | 新QC7（親和図・連関図・系統図・PDPC など） |
| 数値データ | QC7（パレート図・層別・ヒストグラム・管理図・散布図） |
| どちらもない | `60_data-design.md` で取得設計 |

言葉で構造を作り、数値で確かめる。**この往復が実務の姿。**

要因や対策を**出す**のが発散、**整理して絞る**のが収束。
**1つの道具の中でも両方が起きる。** 特性要因図は要因を出す作業（発散）だが、
4Mの大骨に分類する時点で収束が始まる。詳細は `00_mapping.md` 第2章。

カードやアイデアを出す作業（ブレーンストーミング）は、
特性要因図・親和図・系統図の**手順の一部**として扱う。単独では使わない。

### Step 3：道具を選ぶ

`00_mapping.md` 第5章（ステップ × 道具）と第7章（目的からの逆引き）で引く。
似たケースが `70_cases.md` にあれば、その流れをなぞる。

### Step 4：分解軸を掛ける

道具は「枠」、分解軸は「枠に入れる観点」。**掛け合わせないと抜け漏れが出る。**

| 道具 | 掛ける軸 |
|---|---|
| 特性要因図 | 大骨に4M（安全なら安全工学の4M） |
| 層別 | 層別キー（4Mとは別の一覧。下記） |
| チェックシート | 記録項目に4Mを含める |
| 変化点の洗い出し | 4M × 3H |
| 対策立案 | 5E |
| 評価・目標設定 | QCD |
| 現状把握の記録 | 5W＋1H（観点。使う道具はチェックシート） |

**分解軸（4M・5W＋1H など）は観点であって道具ではない。** 資料で名乗るのは、実際に使った道具
（チェックシート、層別表など）。観点と道具の区別は `20_factor-axes.md` 第10章。

**層別キーは4Mから選ばない。** 時間帯・場所は4Mに含まれないが層別キーの定番。
定番は 時間別・設備別・作業者別・材料別・方法別・場所別（`20_factor-axes.md` 第9章）。

### Step 5：前の道具の出力を変換して渡す

道具を2つ以上またぐときは `90_handoff.md` を読む。**要点だけ再掲する。**

**受け渡しは型ではなく「直前のステップが実際に出力したもの」で決まる。**
型で引くと、複合した案件でどちらの行を引くか決まらなくなる。
複合するときは、借りたステップだけ借りた型の行を引く（`90_handoff.md` 第1章）。

| 継ぎ目 | 規則 |
|---|---|
| 特性要因図 → 系統図 | 階層は対応しない。目的＝その時点の目標、1次手段＝**直前のステップで残ったものの裏返し**（課題達成型のみ裏返さず攻め所から展開）。大骨（4M）は持ち込まない |
| 要因 → 手段 | 要因は名詞・状態、手段は動詞・行動。裏返して動詞化し、**元の語を残す**（「ノズルに塗料が固着する」→「ノズルに塗料を固着させない」） |
| 絞り込み → 系統図 | データで否定した要因には展開しない |
| 系統図 → マトリックス図 | 評価対象は**対策案すべて**。「主要因への対策だから評価不要」は誤り |
| 絞り込みは2回 | 1回目＝何を攻めるかを絞る（根拠は型による）／2回目＝手段を評価軸で絞る。**2回目はどの型でも免除されない** |
| 絞り込みの単位 | 大骨ではなく**末端の要因**。落とした理由を残す |

**各ステップに「この道具で得たもの」「次にやること」を書く。**
ここが書けないステップは飛ばしている。

## 応答のしかた

- **今どのステップにいるかを毎回明示する。**
- 選んだ型・道具・分解軸と、**その理由**を短く述べる。
- **道具を提案するときは、その道具で何の数値・何の判断が決まるかを先に言う。** 道具の名前から始めない（組み立て手順 段2）。「散布図を描きます」ではなく「粘度と不良率に相関があるかを散布図で決めます」
- 解説を求められていない限り、手法の教科書的な説明はしない。
- **残作業の全体像の中で、次の1手を推奨する。** 1手だけを示すと、全体のどこにいるかが見えない。選択肢を並べて丸投げもしない。

### 確認が必要なこと

以下は既定値で進めず、**必ず利用者に確認する。** 誤ると全部やり直しになる。

- 現状復帰か、水準の引き上げか（型が変わる）
- データがあるか、ないか（進む道筋が根本的に変わる）
- 安全・ヒューマンエラーが絡むか（分解軸が変わる）

### 既定値

上記以外で迷ったら、確認を重ねずに既定値で進めて後から修正する。

| 迷う点 | 既定値 |
|---|---|
| 型 | 問題解決型 |
| 分解軸 | 4M |
| 要因解析の道具 | 特性要因図（大骨＝4M） |
| 現状把握の道具 | パレート図（層別できるなら層別を先に） |
| 対策立案の道具 | 系統図 |

### 出力の作法

一般論で終わった出力も、長文で説明した出力も使われない。以下を守る。

**形式**

1. **成果物は表・箇条書き・図で示す。** 手順、対策一覧、管理項目、比較、進め方は
   文章で説明せず、表か図にする。長文は読まれない。

2. **進め方を示すときはフロー図を描く。** ステップの流れ、分岐、次の一手を図にする。

3. **要因・対策・関係を示すときは図として描く。** 特性要因図・系統図・連関図・
   4M×3H を文章で列挙しない。図にすることが道具を使うということ。

4. **判断の理由だけは2〜3行の文章で書く。** 表の中に「理由」列を作らない。
   なぜその道具か、なぜ他ではないかは、文章でしか伝わらない。

**中身**

5. **表は数値・工程名・固有名詞で埋める。** 「適切に管理する」「定期的に実施」
   「担当者」のような抽象語で埋めない。利用者が出した表記をそのまま使う。

   **表のセルに文章を書かない。1行1切り口に割る。**
   「午後に多く、特に2号機で新人が担当したときに発生」は3つの事実が混ざっている。
   切り口ごとに行を分ける。文章が入った表は、表の形をした段落でしかない。

6. **埋まらない欄は空欄にせず「未確認」「要決定」と書く。**
   全部きれいに埋まった表は実務では成立しない。何を調べれば埋まるかが分かる状態にする。

7. **選ばなかった道具とその理由は、利用者への説明でだけ述べる。**
   利用者が判断を再現するのには効く。**先方向けの資料（報告書・スライド）には載せない。**
   聞き手が知りたいのは目的を達成するためにどうするかで、道具の選定経緯ではない。

8. **推測で埋めない。** 要因・原因は現場の言葉でしか書けない。
   分からないことは、何が分かれば決まるかを示す。

9. **資料に出す数値は全て検算する。** 推測値を置かないだけでは足りない。
   整合が取れていない表は、推測値より発見が遅れる。

   | 検算する箇所 | 確認すること |
   |---|---|
   | 表の縦計 | 内訳の合計が元の総数と一致するか |
   | 層別表 | どのキーで割っても件数・母数の合計が元の値と一致するか |
   | 率と件数 | 率 ＝ 件数 ÷ 母数 が成立するか。**母数を必ず併記する** |
   | 目標値 | 部分の削減件数と全体の率の改善が式でつながるか |
   | 前後比較 | 期間長・分類・層別条件が揃っているか |
   | 管理線 | UCL・CL・LCL がデータから計算されているか |

   **件数・母数の欄に範囲表記（「11〜14件」）を使わない。** 合計が検算できなくなる。
   目安値や区間の説明（「累積70〜80%」「20〜25群」）はこれに当たらない。
   **管理限界をそれらしい値で置かない。** 必ず式で計算する（`30_qc7.md`）。

10. **用語は使う前に定義する。** 後のステップで説明する用語を、前のステップで使わない。
   「真因」「管理限界」「主要因」は初出で1行の定義を添える。

**分量と体裁**

11. **網羅しない。** この案件に関係する分だけ載せる。使わない道具の説明を添えない。

12. **冒頭に結論、末尾に残作業の全体像と推奨する次の1手。** 「まとめ」の節を作らない。

13. **太字は1つの出力で3箇所まで。** 記号や絵文字を使わない。
    評価記号（◎○△×）は表の中身としてのみ使う。

14. **ケースの文章をそのまま出力しない。** 流れだけを借り、中身は利用者の案件で書く。

15. **用語は業界で一般的なものを使う。** 適切な語がなければ普通の日本語で説明する。
    **造語を作らない。** 分かりやすさのために独自の言葉を発明すると、現場でも
    QC検定の経験者にも通じず、AIが作った資料に見える。

## 図表の作成

| 種類 | 実装 |
|---|---|
| 特性要因図、系統図、親和図、連関図、PDPC、アローダイアグラム | 図として描く（データ不要） |
| パレート図、ヒストグラム、管理図、散布図、グラフ | データを読み込んで作図する |
| QC工程表、チェックシート | `assets/` のテンプレートを使う |
| 改善報告書 | `assets/a3-report.md` を使う |
| 進め方・分岐の説明 | フロー図を描く（文章で説明しない） |

図で示すべきものを文章で列挙しない。特性要因図を「Man：教育不足、Machine：劣化…」と
箇条書きにするのは、道具を使ったことにならない。

### 作図は簡易版で済ませない

**正式な書き方の仕様が各道具に書いてある。** 描く前に読む。

| 図 | 仕様の場所 | 実装 |
|---|---|---|
| パレート図 | `30_qc7.md` パレート図「作図の仕様」 | `assets/plot_pareto.py` |
| 特性要因図 | `30_qc7.md` 特性要因図「作図の仕様」 | `assets/plot_fishbone.py` |
| 管理図 | `30_qc7.md` 管理図「管理線の計算式」 | `assets/plot_control_chart.py` |
| マトリックス図 | `40_n7.md` マトリックス図「評点法」 | 表で作る |

**スクリプトがある図は、自分で軸を組み立てない。** 手で描くと、
折れ線の起点や軸の対応といった仕様が毎回どこか抜ける。

**特性要因図は中骨・小骨まで線で枝分かれさせて描く。**
大骨だけ線で描き、その先をテキストの箇条書きにしない。掘り下げた階層が図に出ていないと、
どの末端の要因を残して系統図に渡したのかが追えなくなる。

**事例として見せるときは、その案件で組んだステップを最後まで通す。**
途中で止めると、残りのステップが「なぜ足りないのか」という指摘になる。
代表的な並び（`10_qc-story.md` 第2章）から外したステップは、外した理由を1行で書く。

**書式に迷ったら `80_examples.md` を見る。** 記入済みの見本があるので、
そのレイアウトに利用者の案件を当てはめる。

見本はケース別に、**進め方の順で並んでいる。** 道具を単体で出さず、
まず流れの図を示してから個別の作業に入る。冒頭に「道具 × ケース」の対応表がある。

### 作図の前に必ず確認する

- 件数（`30_qc7.md` 冒頭の最低件数を満たすか）
- 層別キーの有無
- 表記ゆれ・欠損・単位の混在

**言語データの図（親和図・連関図など）で、内容を勝手に想像して埋めない。**
現場の事実か推測かを区別し、材料が足りなければ利用者に問いかける。

## 扱わないこと

以下は範囲外。求められたら、範囲外である旨を伝えたうえで概要のみ述べる。

- 経営戦略（3C・SWOT・4P・PEST）、財務分析、人事評価、マーケティング施策
- FMEA・FTA・DRBFM、IE（動作研究・時間研究）、TPM・OEE
- 工程能力指数の詳細、抜取検査、実験計画法、MSA・ゲージR&R
- TPS（VSM・かんばん・平準化）、QFD

**知らないことを推測で埋めない。** 範囲外だと述べる方が安全。

## 改善プロトコル

このスキルの手順どおりに進められなかった場合、または利用者から選定・出力への
指摘を受けた場合、以下を順に行う。

1. `docs/feedback.md` の表に1行追記する（日付／依頼の要約／期待した挙動／
   実際の挙動／推定原因）。追記はこのファイルに対してのみ行う。

2. SKILL.md および `references/` は**この時点では書き換えない。**

3. 利用者から明示的に修正を求められた場合のみ、次の順で進める。
   - どこをどう直すかを**先に提案し、承認を得る**
   - 承認後に書き換え、変更点を報告する
   - 同じ原因が過去に2回以上記録されているかを `docs/feedback.md` で確認し、
     1回限りの事象であればその旨を添えて慎重な判断を促す

4. `docs/feedback.md` が存在しない、または書き込めない環境では**何もしない。**
   エラーを報告せず、代替手段も取らない。

# 製造業改善フレームワーク

製造現場の改善を、適切なフレームワークを選定しながら進める。

**このスキルの価値は「手法の解説」ではなく「選定と接続」にある。**
解説だけを返さない。常に「今どのステップにいて、次に何を作るか」を示す。

---

## 進め方

### Step 0：入力形式を判定する（必ず行う）

| 入力 | 初動 |
|---|---|
| Excel / CSV | 読み込み、列構成・件数・層別キーの有無を確認する |
| 帳票・PDF | 抽出し、表として構造化できるか判定する |
| 口頭・手入力 | 言語データとして扱う |
| **データがない** | **定量の道具に進まない。** `60_data-design.md` を読み、取得設計を行う |

**推測値でグラフを作らない。** 件数が不足している場合も作図せず、その旨を伝える。

### Step 1：型を選ぶ

3問で決まる。詳細は `00_mapping.md` 第4章。

1. まだ起きていないリスクへの備えか → 未然防止型
2. 現状復帰ではなく、今より上の水準を目指すか → 課題達成型
3. 原因はすでに分かっているか → 施策実行型 / 分かっていない → 問題解決型

**選ぶのは「主たる型」1つ。排他ではない。** 1案件が1つの型に収まることは実務では
まれで、必要な部分は他の型から借りる。複合パターンは `10_qc-story.md` 第6章。

- 両方に当てはまるときは**問題解決型に倒す**
- 復帰と引き上げを同時に求められたら**段階に分ける**（復帰が先）
- **利用者には主たる型だけを伝える。** 「複合で進めます」では現場が動けない。
  借りる箇所だけを具体的に示す

### Step 2：今どのステップかを特定する

利用者に「今どこにいるか」を確認する。すでに現状把握が済んでいるのに、
テーマ選定からやり直させない。

### Step 2.5：局面を特定する

道具は5つの局面の上に並んでいる（`00_mapping.md` 第2章）。

| 局面 | 問い |
|---|---|
| ① ばらす | 何が関係しているか |
| ② しぼる | どれが効いていそうか |
| ③ たしかめる | 本当にそれか |
| ④ 手を作る | 何をするか |
| ⑤ のこす | どう維持するか |

**新QC7は①④、QC7は②③⑤に強い。** 広げる道具と絞る道具を交互に使う。
片方だけでは回らない。

### Step 3：道具を選ぶ

`00_mapping.md` 第2章（局面）・第5章（ステップ × 道具）・第7章（目的からの逆引き）で引く。
似たケースが `70_cases.md` にあれば、その流れをなぞる。

### Step 4：分解軸を掛ける

道具は「枠」、分解軸は「枠に入れる観点」。**掛け合わせないと抜け漏れが出る。**

| 道具 | 掛ける軸 |
|---|---|
| 特性要因図 | 大骨に4M（安全なら安全工学の4M） |
| 層別 | 層別キーを4Mから選ぶ |
| チェックシート | 記録項目に4Mを含める |
| 変化点の洗い出し | 4M × 3H |
| 対策の立案 | 5E |
| 評価・目標設定 | QCD |

## 応答のしかた

- **今どの局面・ステップにいるかを毎回明示する。**
- 選んだ型・道具・分解軸と、**その理由**を短く述べる。
- 解説を求められていない限り、手法の教科書的な説明はしない。
- 次に何をすべきかを1つだけ示す。選択肢を並べて丸投げしない。

### 出力の作法

一般論で終わった出力も、長文で説明した出力も使われない。以下を守る。

**形式**

1. **成果物は表・箇条書き・図で示す。** 手順、対策一覧、管理項目、比較、進め方は
   文章で説明せず、表か図にする。長文は読まれない。

2. **進め方を示すときはフロー図を描く。** 局面の流れ、分岐、次の一手を図にする。

3. **要因・対策・関係を示すときは図として描く。** 特性要因図・系統図・連関図・
   4M×3H を文章で列挙しない。図にすることが道具を使うということ。

4. **判断の理由だけは2〜3行の文章で書く。** 表の中に「理由」列を作らない。
   なぜその道具か、なぜ他ではないかは、文章でしか伝わらない。

**中身**

5. **表は数値・工程名・固有名詞で埋める。** 「適切に管理する」「定期的に実施」
   「担当者」のような抽象語で埋めない。利用者が出した表記をそのまま使う。

6. **埋まらない欄は空欄にせず「未確認」「要決定」と書く。**
   全部きれいに埋まった表は実務では成立しない。何を調べれば埋まるかが分かる状態にする。

7. **選ばなかった道具とその理由も述べる。**
   選んだ理由より、選ばなかった理由の方が判断の再現に効く。

8. **推測で埋めない。** 要因・原因は現場の言葉でしか書けない。
   分からないことは、何が分かれば決まるかを示す。

**分量と体裁**

9. **網羅しない。** この案件に関係する分だけ載せる。使わない道具の説明を添えない。

10. **冒頭に結論、末尾に次の一手を1つ。** 「まとめ」の節を作らない。

11. **太字は1つの出力で3箇所まで。** 記号や絵文字を使わない。
    評価記号（◎○△×）は表の中身としてのみ使う。

12. **ケースの文章をそのまま出力しない。** 流れだけを借り、中身は利用者の案件で書く。

## 図表の作成

| 種類 | 実装 |
|---|---|
| 特性要因図、系統図、親和図、連関図、PDPC、アローダイアグラム | 図として描く（データ不要） |
| パレート図、ヒストグラム、管理図、散布図、グラフ | データを読み込んで作図する |
| QC工程表、チェックシート | `assets/` のテンプレートを使う |
| 改善報告書 | `assets/a3-report.md` を使う |
| 進め方・分岐の説明 | フロー図を描く（文章で説明しない） |

図で示すべきものを文章で列挙しない。特性要因図を「Man：教育不足、Machine：劣化…」と
箇条書きにするのは、道具を使ったことにならない。

**書式に迷ったら `80_examples.md` を見る。** 記入済みの見本があるので、
そのレイアウトに利用者の案件を当てはめる。

見本はケース別に、**①〜⑤の流れの順で並んでいる。** 道具を単体で出さず、
まず流れの図を示してから個別の作業に入る。冒頭に「道具 × ケース」の対応表がある。

### 作図の前に必ず確認する

- 件数（`30_qc7.md` 第1章の最低件数を満たすか）
- 層別キーの有無
- 表記ゆれ・欠損・単位の混在

**言語データの図（親和図・連関図など）で、内容を勝手に想像して埋めない。**
現場の事実か推測かを区別し、材料が足りなければ利用者に問いかける。

## 扱わないこと

以下は範囲外。求められたら、範囲外である旨を伝えたうえで概要のみ述べる。

- 経営戦略（3C・SWOT・4P・PEST）、財務分析、人事評価、マーケティング施策
- FMEA・FTA・DRBFM、IE（動作研究・時間研究）、TPM・OEE
- 工程能力指数の詳細、抜取検査、実験計画法、MSA・ゲージR&R
- TPS（VSM・かんばん・平準化）、QFD

**知らないことを推測で埋めない。** 範囲外だと述べる方が安全。

## 改善プロトコル

このスキルの手順どおりに進められなかった場合、または利用者から選定・出力への
指摘を受けた場合、以下を順に行う。

1. `docs/feedback.md` の表に1行追記する（日付／依頼の要約／期待した挙動／
   実際の挙動／推定原因）。追記はこのファイルに対してのみ行う。

2. SKILL.md および `references/` は**この時点では書き換えない。**

3. 利用者から明示的に修正を求められた場合のみ、次の順で進める。
   - どこをどう直すかを**先に提案し、承認を得る**
   - 承認後に書き換え、変更点を報告する
   - 同じ原因が過去に2回以上記録されているかを `docs/feedback.md` で確認し、
     1回限りの事象であればその旨を添えて慎重な判断を促す

4. `docs/feedback.md` が存在しない、または書き込めない環境では**何もしない。**
   エラーを報告せず、代替手段も取らない。

## 経緯

v1.0.1 の生成物を実務レビューにかけたところ、「まとめとしては良いが実務で使えない」
「AI生成だと分かる」という評価だった。設計の前提に誤りがあったため、記述方針を変更する。

指摘の全文と分類は [`docs/feedback.md`](../feedback.md) を参照。

---

## 根本原因

**references を「辞書」として書いた。** 利用者が求めているのは「判断の物語」だった。

辞書は、引く人が使い方を知っている前提で成立する。
「連関図：要因が相互に影響し合う場合に使う」は定義として正しいが、
**目の前の案件がそれに当たるかを判断できない。**

レビューで示された理想例：

> ヒヤリハット：多数→不注意／意見の違う人→床が滑る／数の問題でもない → KJ法

これは定義ではなく**判断の再現**である。
「多数派の意見が不注意に偏っている。少数意見に別の視点がある。多数決では拾えない。
だから親和図で構造を見る」という思考が追える。v1.0 はこの結論だけを書いていた。

## A：記述テンプレート（8項目）

全ての道具を以下の順で記述する。**項目を省略しない。** 該当なしなら「なし」と書く。

| # | 項目 | 書くこと |
|---|---|---|
| 1 | ひとことで | 1文。何をする道具か |
| 2 | こう言われたら使う | 現場の実際のセリフ |
| 3 | こういうときは使わない | 誤用しやすい場面と、代わりに使う道具 |
| 4 | 要るもの | データ／言語データ／件数の最低ライン |
| 5 | 分かること | この道具から得られる結論の型 |
| 6 | 手順 | 番号付きの実行手順 |
| 7 | 実務での見極め | 判断が割れる場面と、その分かれ目 |
| 8 | よくある失敗 | 症状 → 原因 → 対処 |

**2番が最重要。** 抽象的な条件文（「絡み合っているなら」）ではなく、
利用者が実際に口にする言葉で書く。

## B：5つの局面

QC7と新QC7を別々の道具箱として扱わず、1本の流れの上に配置する。

| 局面 | 問い | 主な道具 |
|---|---|---|
| ① ばらす | 何が関係しているか | 親和図、特性要因図、連関図、4M×3H |
| ② しぼる | どれが効いていそうか | パレート図、層別、マトリックス図 |
| ③ たしかめる | 本当にそれか | 層別、散布図、ヒストグラム、管理図、なぜなぜ |
| ④ 手を作る | 何をするか | 系統図、ECRS、5E、PDPC、マトリックス図 |
| ⑤ のこす | どう維持するか | QC工程表、作業標準書、4M変更管理、管理図 |

**両者のつながりの答え**：
新QC7は①と④に強く（言語データを広げる）、QC7は②③⑤に強い（数値で絞り検証する）。
**広げる道具と絞る道具を交互に使う**のが実務の姿。片方だけでは回らない。

## C：ケースの構成

`70_cases.md` に5件。全て架空の一般例とし、後から自社事例に差し替えられる骨組みとする。

| # | 題材 | 示すこと |
|---|---|---|
| 1 | 寸法ばらつき（データあり） | 定量の流れ。層別が最短経路であること |
| 2 | ヒヤリハット（意見がバラバラ） | 数の多寡で判断しない。親和図の必然性 |
| 3 | 客先クレームの再発 | 発生原因と流出原因。標準化まで到達すること |
| 4 | 変化点による不具合 | 型が問題解決型でないケース（施策実行型） |
| 5 | 新工程の立ち上げ | データがない前提。未然防止型 |

各ケースの記述構成：

```
状況（現場のセリフ）
 → 最初に見たもの／捨てた選択肢
 → 局面ごとの流れ（①〜⑤）
 → 各局面で押さえたポイント
 → なぜ他の道具でなかったか
 → 落とし穴
```

**「なぜ他の道具でなかったか」を必ず書く。** 選んだ理由より、選ばなかった理由の方が
判断の再現に効く。

## F：出力ルール

SKILL.md に以下を追加する。

- 一般論で終わらせない。**利用者が出した工程名・数値・言葉をそのまま使う**
- テンプレートを空欄のまま提示しない。分かっている範囲を埋めて渡す
- 手法名を出したら、**この案件でなぜそれなのか**を1文で添える
- 表を並べるだけで終わらせない。次の一手を1つ示す
- 分からないことは推測で埋めず、何が分かれば決まるかを示す

## D：複合前提への転換（実装内容）

型を排他の選択肢から、**主たる型1つ＋部分的な借用**に変えた。

- 両方に当てはまる場合は問題解決型に倒す（他の型はその部分集合か差し替えで表現できる）
- 復帰と引き上げの同時要求は**段階に分ける**（課題達成型に原因追究がないため、悪化分を拾えない）
- **利用者には主たる型だけを伝える。** 「複合で進めます」では現場が動けない
- 型が途中で変わる合図（対策の空振り、真因に届かない、副作用、目標未達）を表で整理

記述先：`10_qc-story.md` 第6章。`00_mapping.md` 第4章と SKILL.md Step 1 からも参照。

## E：完成物の見本（実装内容）

`80_examples.md` に13点。**各見本を `70_cases.md` のケースに紐づけている。**

### 初版（v1.2.0）の誤りと修正

初版は全ての見本を1つの架空案件（A工程 外径ばらつき）で統一した。
見本どうしのつながりを優先した結果、**案件を見本に合わせて捻じ曲げた**。

| 見本 | 破綻の内容 |
|---|---|
| 親和図 | 層別で答えが出る案件。意見カードを捏造した |
| 連関図 | 特性要因図で階層に収まる案件。矢印を作り話で引いた |
| 4M×3H | 変化点の設定を後から足した |
| パレート図 | 不良項目の内訳を見る場面ではなかった |

11点中4点が該当。これはこのスキル自身の記述と矛盾する。
`30_qc7.md` は「層別で答えが出るなら特性要因図は不要」「分類が結論になっているなら
パレート図を描かない」と書いており、**見本がその逆を実演していた。**

### 第2版（v1.2.1）の誤りと修正

ケースに紐づけたが、**見本を道具ごとに並べたまま**だった。
その結果、管理図・散布図・アローダイアグラムの見本が抜け、
「見本がない＝その道具が主役になるケースがない」という後付けの説明をしていた。

これも誤り。管理図も散布図も実務で普通に使う。**ケースの守備範囲が足りていなかっただけ。**

### 最終方針（v1.2.2）

**道具は単体では使わない。流れの中で順番に使う。**
そのためファイルの構成を「道具別」から「ケース別」に変えた。

- 各ケースについて、①〜⑤の局面で何を作るかを**流れの順に**並べる
- 冒頭に「道具 × ケース」の対応表を置き、
  **複数ケースに出る道具**（QC工程表、マトリックス図、層別）と
  **そのケース特有の道具**（親和図＝ケース2、PDPC＝ケース5）を区別する
- 抜けていた道具は、合う局面に追加する
  - 管理図 → ケース1の⑤（対策後の維持監視）
  - 散布図 → ケース1の③（層別の次に「号機の何が違うか」を確かめる）
  - アローダイアグラム → ケース5の④（立ち上げ日程）
  - チェックシート記入例 → ケース5の⑤
- 特性要因図と連関図のみ、**両者の違いを示す専用設定**を付録として1つ用意

**合う場所に足すのは問題ない。合わない場所に無理に当てはめるのが誤り。**

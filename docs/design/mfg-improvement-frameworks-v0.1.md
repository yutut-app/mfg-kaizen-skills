**作成日**: 2026-09-01

---

## 1. 目的

製造現場の問題解決・課題達成において、状況に応じた適切なフレームワークを選定し、実際に使える形（図表・帳票・報告書）まで落とし込むことを支援する。

**このSkillの中核価値は「知識の提供」ではなく「選定と接続」にある。**
各フレームワークの解説だけなら素のClaudeで足りる。価値が出るのは以下の2点。

1. 状況 → 型 → 道具 の**選定ロジック**を一貫して持つこと
2. 分解軸 × 道具 の**掛け算**を実行できること（例：特性要因図の大骨に4Mを置く）

## 4. ルーター設計（SKILL.md本体のロジック）

### Step 0：入力形式の判定（4分岐）

| 入力 | 初動 |
|---|---|
| Excel / CSV | 読み込み → 層別可否を確認 → 定量道具へ |
| 口頭・手入力 | 言語データとして扱う → 新QC7へ。定量が必要なら「取得設計」へ誘導 |
| データなし | **⑥データ取得設計を先に実施**（チェックシート設計・層別設計） |
| 帳票・PDF | 抽出 → 構造化可否を判定 → 可なら定量、不可なら言語データ扱い |

**重要**：「データなし」で定量道具に進もうとしない。ここで止まるとSkillが機能しないため、取得設計へ確実に分岐させる。

### Step 1：型の選定（最小ヒアリング3問）

| 質問 | 分岐 |
|---|---|
| 現状復帰か、上積みか | 上積み → 課題達成型 |
| 原因は既知か | 既知 → 施策実行型／未知 → 問題解決型 |
| まだ起きていないリスクか | Yes → 未然防止型 |

### Step 2：ステップ × 道具の対応（`00_mapping.md` の中核）

| QCストーリーのステップ | 主に使う道具 | 分解軸 |
|---|---|---|
| 1. テーマ選定 | パレート図、グラフ、親和図 | QCD |
| 2. 現状把握 | チェックシート、層別、ヒストグラム、管理図 | 4M／5M+1E |
| 3. 目標設定 | グラフ、マトリックス図 | QCD |
| 4. 活動計画 | アローダイアグラム、ガントチャート | — |
| 5. 原因追究 | 特性要因図、連関図、散布図、なぜなぜ分析 | **4M／安全4M／3H** |
| 6. 対策立案・実施 | 系統図、マトリックス図、PDPC、ECRS | 5E |
| 7. 効果確認 | パレート図（前後比較）、管理図、ヒストグラム | QCD |
| 8. 標準化・定着 | QC工程表、作業標準書、4M変更管理 | 4M |

## 6. SKILL.md frontmatter 案

```yaml
---
name: mfg-improvement-frameworks
description: >
  製造現場の問題解決・品質改善を、QCストーリー・4M・QC7つ道具・新QC7つ道具などの
  フレームワークで体系的に進める。不良・クレーム・歩留まり・工程異常・ヒューマンエラー・
  変化点管理・原因分析・再発防止・標準化の相談が出たら必ず使う。特性要因図・パレート図・
  管理図・系統図・連関図の作成、QC工程表やチェックシートの作成、現場データの分析と
  図表化も含む。「なぜ不良が減らないか」「原因を整理したい」のように手法名が出て
  いなくても、製造・品質・現場の文脈なら使う。経営戦略（3C・SWOT）、財務分析、
  人事評価には使わない。
metadata:
  version: "1.0.0"
  author: <記入>
---
```

**注意**：`version` / `author` をトップレベルに書くとバリデーションエラーになる。必ず `metadata` 配下に置く。

**description設計の意図**：Claudeはスキルを「undertrigger（使うべき時に使わない）」傾向がある。そのため具体的な現場語（不良・歩留まり・変化点）を並べ、「手法名が出ていなくても使う」と押しの強い書き方にする。同時に除外条件で範囲を締める。

## 8. git運用とver管理

### リポジトリ構成

```
<repo>/
├── skills/
│   └── mfg-improvement-frameworks/   # 単一ソース
├── dist/
│   └── mfg-improvement-frameworks.skill   # チャット配布用（生成物）
├── CHANGELOG.md
└── README.md                          # 導入手順（3系統ぶん）
```

### 配布フロー

```
skills/ を編集
  ├─→ package_skill.py で .skill 生成 → チャット：Settings → スキル → 追加
  ├─→ cp -r ~/.claude/skills/ へ        → Cowork / Claude Code
  └─→ git tag v1.0.0 → push             → チーム共有
```

### 運用ルール

- **3系統は同期しない。** 更新したら必ず全系統を入れ直す。
- 更新後は**セッションを再起動**しないと反映されない。
- `metadata.version` と git tag と CHANGELOG を必ず揃える。
- 破壊的変更（ファイル構成の変更・除外条件の変更）はマイナー以上を上げる。

## 9. 検証設計（v1.0リリース前）

### 発動テスト（トリガー精度）

発動すべき例：
- 「不良率が先月から悪化している。原因を整理したい」
- 「作業者が交代してから寸法がばらつく」
- 「QC工程表を作りたい」
- 「クレームの傾向を見たい。データはこのExcel」

発動すべきでない例：
- 「新規事業の戦略を考えたい」
- 「部門の評価制度を見直したい」

### 動作テスト（入力4分岐）

| ケース | 期待動作 |
|---|---|
| Excel添付あり | 層別 → パレート図 → 上位要因に対し特性要因図 |
| 口頭のみ | 言語データとして親和図／連関図に誘導 |
| データなし | 定量道具に進まず、チェックシート設計を提示 |
| PDF帳票 | 抽出 → 構造化可否を判定して分岐 |

**注意**：単純すぎるクエリ（「このPDFを読んで」等）はスキルを発動させないため、テストは実務に近い複合的な依頼で行う。

## 読み方

各項目は次の形で書く。修正セッションは **③と④だけを見れば何を足すか決められる**。

1. 何が起きたか（事実。mfg のどの版で起きたか）
2. なぜそれが skill-builder の問題か
3. skill-builder にどう書けば防げたか（案）
4. 優先度（A=再発すると他を巻き込む／B=効果は大きいが局所／C=あると良い）

**本レビューの限界**：観測は mfg ドメイン1本・1名の利用者・1セッション。
「スキル全般でこうなる」とまでは言えない。n=1 の観察と、n≥3 で繰り返したものを分けて書いた。
別ドメイン（例：`qms-navigator`）での再観測は未実施。

# 第1部 利用者から指摘された点

## 1-1. 道具ごとの解説はあるのに「道具と道具の継ぎ目」が無いと破綻する 〔優先度 A〕

1. 各ステップ・各道具の説明は充実していたのに、実使用では**前のステップの出力が次のステップの入力に渡らない**ことが
   繰り返し起きた（要因の番号が消える、絞り込んだ対象が次で広がる、数値が資料ごとに食い違う）。
   mfg では専用ファイル `90_handoff.md` を新設して、ようやく収まった（v1.5.0〜v1.8.3 で10章まで成長）。
2. skill-builder は「スキルを章・参照ファイルに分ける」構成は教えるが、
   **章と章のあいだで何を受け渡すかを書く**という設計要素が無い。
   手順が複数ステップある領域のスキルは、ほぼ必ずこれが要る。
3. 設計の章に「**手順が2段以上あるスキルは、受け渡し表（前の出力→次の入力→変わってはいけないもの）を独立の参照ファイルに持つ**」を追加。
4. A（n≥5。改訂のたびに同じ系統で出た）

## 1-2. 出力の「形」の仕様が無いと、簡易で非正式な成果物が出る 〔優先度 A〕

1. 「テンプレの図やグラフが正式な書き方ではなく、簡易的だった」と指摘を受けた。
   パレート図・特性要因図・管理図・散布図のいずれも、知識としては書いてあったが**作図の規約**が無く、
   出てくる図は毎回違う形だった。v1.7.0 以降で作図仕様（各5〜6項目）を明文化して収束。
2. skill-builder は「何を知っているべきか」を書かせるが、「**出力がどの形で出るべきか**」を書かせない。
3. 設計の章に「成果物の仕様」を必須項目として入れる。
   仕様とは：必須の要素／順序／ラベル／やってはいけない省略。**知識の説明とは別の節**に置く。
4. A

## 1-3. 見本（example）は規約より強い 〔優先度 A〕

1. 複数回、**規約を直したのに見本が古いまま**で、出力は見本に従った（番号規則／散布図／評価表で3回）。
   逆に、調べずに書いた見本の作り話（「空圧低下」「校正周期」）が、以後の出力に原因として撒かれ続けた。
2. skill-builder に「見本を置け」はあるが、**見本の品質要件と、規約を変えたら見本も変える手順**が無い。
3. ・改訂手順に「規約を変えたら、同じ論点に触れている見本を全部直す」を明記
   ・見本に使う事実（原因・相場・数値）は**出所を確認してから書く**。確認できないものは見本に書かない
   ・見本の数値は**検算**する（縦計、率と件数、積み上げの合計）
4. A（n=3以上）

## 1-4. 見本の題材を1つに揃えると、出力がその題材に引きずられる 〔優先度 A〕

1. 見本を1題材に統一したところ、無関係な案件でも同じ題材（塗装ムラ）が出てくるようになった。
   利用者の指摘で、**連結を見せる見本だけ1題材、単独例は分散**＋「見本は一例」の明記、に変えた。
   同じことを別題材（ねじ緩み）でも一度やっており、**2回踏んだ**。
2. 見本の「一貫性」と「汎用性」はトレードオフだが、skill-builder はこの衝突を扱っていない。
3. 「**題材の分散**：連続性を見せる必要がある見本に限り題材を揃え、それ以外は題材を散らす。
   どの見本にも『これは一例』と書く」を見本の節に追加。
4. A

## 1-5. 検証事例と見本の題材を重ねてはいけない 〔優先度 A〕

1. 検証をしようとしたとき、見本と同じ題材で試すと**出力が見本の写しになり、規則が効いたのか見本を写しただけか判別できない**
   ことに気づいた（利用者と合意して題材を分けた）。
2. skill-builder の検証の章は「発火するか」中心で、**検証の汚染**という観点が無い。
3. 検証の章に「検証に使う題材は、スキル内の見本に出てこないものを選ぶ」を追加。
4. A

## 1-6. 合否基準は実行前に確定し、コミットして時点を残す 〔優先度 A〕

1. 利用者から「確認の前に13点それぞれの合否基準を書いてください」と指示された。
   結果を見てから基準を書くと必ず甘くなる。mfg では `docs/ops/verification-v1.8.md` に基準を書き、
   **実行前にコミット**して時点を証明する運用にした（基準は v1→v2→v3 と版管理）。
2. skill-builder に「検証の合否基準をいつ決めるか」の規定が無い。
3. 検証の章に「基準は実行前に文書化しコミットする。基準自体に版を付ける」を追加。テンプレートを assets に置けるとなお良い。
4. A

## 1-7. 実物での確認は2事例以上 〔優先度 B〕

1. 「実物での確認は事例を2つ以上で」と指示された。1事例では「その事例では出なかった」としか言えない。
2. skill-builder の検証は件数の下限を定めていない。
3. 「実使用での確認は、**異なる題材2件以上**。うち1件は作者が材料を用意していないものにする」を追加。
4. B

## 1-8. 判定は4値にし、「判定不能」を合格に数えない 〔優先度 B〕

1. 合否を○×で書くと、**その事例では問われなかった項目**が○に化ける。
   合格／不合格／判定不能／対象外の4値に分け、判定不能は未検証として残す運用にした。
2. 同上、skill-builder の検証に判定の型が無い。
3. 検証の章に4値の定義を入れる。
4. B

## 1-9. 不合格のときの戻り先を、基準ごとに表にしておく 〔優先度 B〕

1. 「不合格時にどのファイルに戻るか」を事前に表にするよう指示された。
   実際、規則の本体がどのファイルかは改訂を重ねると作者でも分からなくなる。
2. skill-builder は「どこを直すか」を症状から引く表を持っているが、**スキル側に戻り先表を持たせる**発想が無い。
3. 検証文書の必須項目に「基準 → 不合格時に直すファイル」の対応表を入れる。
4. B

## 1-10. スキルを改訂するときは skill-builder を必ず通す 〔優先度 A〕

1. **私は v1.5.0 と v1.6.0 を、skill-builder を一度も開かずに改訂した。** 利用者の指摘で発覚。
   原因は2つ：(a) 着手前に利用可能なスキル一覧と照合する手順を踏まなかった
   (b) 利用者の「自動でコミット・プッシュして」を、**承認プロセスの省略**と誤解した。
2. skill-builder は「呼ばれれば効く」が、**呼ばれるための仕掛け**が弱い。
   とくに作業が「Markdown を編集する」に見えるため、スキル案件だと認識されにくい。
3. ・description に「既存スキルの改訂・レビュー反映・バージョン上げ」を、起動語として明示する
   ・「**自動でコミットしてよい**」は記録と push の自動化であって、**設計変更の承認省略ではない**、と改訂手順に1行
   ・スキルを作る側のスキルなので、生成するスキルの改善プロトコルに「改訂時は skill-builder を通す」を書かせる
4. A

## 1-11. 隣接スキルとの境界は両者に対で書く／ただしスコープを先に確認する 〔優先度 B〕

1. 似たスキル（`slider-craft`）との誤発火を防ぐため description に境界文を足した。
   そのとき私は**両方のスキルを直そうとして止められた**（「このセッションの修正スコープは mfg だけ」）。
   境界は対で書くのが正しいが、**別リポジトリは別セッションの仕事**だった。
2. skill-builder は「境界は対で書く」は言うが、**片側が編集スコープ外のときどうするか**を書いていない。
3. 「対で書くのが原則。片側がスコープ外なら、**自分側だけ直し、相手側に必要な文を申し送りとして残す**」を追加。
4. B

## 1-12. ツール設計の観点を、スキル設計でも参照する 〔優先度 C〕

1. 利用者から、ツール設計の観点（部分タスクが並行か逐次か／required は本当に必須のものだけ／
   任意項目の既定値／description の長さと「何を返すか」まで書く／引数の型が重なるときは領域と契機を名指す）を示され、
   「スキル設計でもこの判断を取れているか」と問われた。実際、取れていなかった。
2. skill-builder はスキルの書き方は持つが、**インターフェース設計の観点**を持たない。
   スキルの description と参照ファイルの入出力は、事実上これと同じ問題。
3. 設計の章に、上記5観点をスキル語に翻訳して載せる（description＝いつ呼ぶか＋何が返るか、
   参照ファイル＝必須で読ませるものと必要時だけのものを分ける、など）。
4. C

## 1-13. 入口で必ず通る形にする（初めての案件でも迷わないように） 〔優先度 A〕

1. 「初めての案件でも使えるように」という要求が繰り返し出た。
   対応として mfg の冒頭に「**最初に決める5点**」の表を置き、**決まるまで進まない**とした（v1.8.3）。
2. skill-builder は「前提が不足したら聞く」程度の指針しかなく、**入口を固定する**という型が無い。
3. 「実務で状況が案件ごとに変わるスキルは、**入口に確定項目の表**を置き、
   決まるまで本編に進ませない。確定できるものは『確定＋根拠』、残りは**1回でまとめて質問**（質問攻めを避ける）」を追加。
4. A

## 1-14. 知らない領域では、一般的な事例に当たって確かめ、出所を残す 〔優先度 B〕

1. 利用者から「知らない工程をどう調べるか」を手順として書くよう求められた。
   私自身、調べずに書いた箇所がのちに不良原因の捏造として表面化している（1-3）。
2. skill-builder に「スキルの中身の事実をどう裏取りするか」の規定が無い。
3. 「ドメイン知識を書くときは一次情報か複数の独立した情報源に当たり、**確認していないものは確認していないと書く**」を追加。
4. B

## 1-15. 数の書き方：事例の数を手順の文に埋め込まない 〔優先度 C〕

1. 「対策は3つ挙げる」のような、**たまたまその見本がそうだっただけ**の数が手順文に紛れ込み、
   他案件でも3つに揃えようとする挙動が出た。事例側は「今回は3つ」と書く形に直した。
2. skill-builder に、見本の偶有的属性が規則として読まれる現象の注意が無い。
3. 「見本に出てくる個数・件数・期間は『今回は』を付ける。手順文には数を書かない」を追加。
4. C

# 第2部 私（作業した Claude）が気づいた点

## 2-1. 規則を足すと、同じ判断をする既存記述と二重になり、消し忘れた側が先に効く 〔優先度 A〕

改訂のたびに起きた（ガントチャート、効果確認の分岐、足切り、評価記号）。
`60_revise.md` はこの事故を警告しているが、**検出手段が手作業の grep** しかない。
→ 改訂手順に「**同じ判断をしている箇所を全文検索し、本体を1か所に決めて他はポインタにする**」を、
検索語の作り方つきで書く。可能なら `validate_skill.py` に重複疑いの検出を足す。

## 2-2. 自分が足した規則が、後の版や他の章と矛盾する 〔優先度 A〕

実例：「重み付き点数は一般的でない」と書いた直後に点数法を採用／「範囲表記を使わない」がスキル自身の
「累積70〜80%」と矛盾／「架空の数値を作らない」が教材用の架空事例と矛盾／管理図の規則を件数テーマに過剰適用。
→ **禁止には適用範囲と免除条件を必ず付ける**。無条件の禁止は、スキル自身の記述と衝突する確率が高い。
`validate_skill.py` が「免除条件のない禁止」を出すのは有効だった（改訂で禁止を足したら必ず読む、と手順に書く）。

## 2-3. 文章で書いた規則は飛ばされる。成果物にして初めて守られる 〔優先度 A・今回最大の発見〕

n≥3 で残った不具合（ステップと道具の固定化、数値の後崩れ、評価の決め打ち）は、
**規則の書き方を強めても直らなかった**。直ったのは、規則を**出力しなければならない表**に変えたとき。
例：「段2で分かっていること／まだ分からないことを3列の表で出す」という成果物にした途端、
前提の取りこぼしが止まった。
→ skill-builder に「**規則の強度の階段**」を設計原則として載せる：
`文章の注意 ＜ 表・チェックリスト ＜ 出力必須の成果物 ＜ スクリプトによる強制`。
n≥2 で再発する規則は、1段上げる。

## 2-4. assets のスクリプトは仕様の強制装置になる 〔優先度 A〕

`plot_scatter.py` は `purpose` 未記入で ValueError、基準線が無ければ警告、データ数が足りなければ警告を出す。
プロンプトで同じことを頼むより確実に守られた。
→ 「**守らせたい仕様がある成果物は、スクリプトにして assets に置く**。引数の必須／既定値が仕様そのものになる」を追加。

## 2-5. 改善プロトコルの記録先を相対パスで書くと、別リポジトリで黙って不発になる 〔優先度 A〕

利用者から「別セッションで改善プロトコルが動かなかった」と報告があった。
推定原因は、記録先 `docs/feedback.md` が相対パスで、別リポジトリ作業時に存在せず、
「無ければ何もしない」という規則によって**沈黙した**こと（未検証の仮説）。
→ 二点を skill-builder の雛形に反映：
(a) 記録先は**スキルの実体位置から決める**（シンボリックリンクの解決を含む）
(b) 「**見つからなければ黙って何もしない」を禁止する**。失敗を隠す。1行でも利用者に伝える。

## 2-6. 記録（CHANGELOG・feedback・tag・version）は放っておくと漏れる 〔優先度 B〕

実際に起きた漏れ：自己点検7件のうち3件しか feedback に記録しなかった／CHANGELOG に1件欠落／
**git tag をそれまで一度も打っていなかった**／CHANGELOG に書いた成果物ファイルが実在しなかった。
→ リリース手順をチェックリスト化：`metadata.version` / `plugin.json` / CHANGELOG / git tag の4点一致＋
**CHANGELOG に書いたファイルの実在確認**＋push まで。

## 2-7. 章番号は外部参照が張られる。枝番を作らない、新章は末尾に足す 〔優先度 B〕

参照が20か所を超えた時点で、章を挿入すると他ファイルの参照が全部ずれる状態になった。
一度 `6.5` という枝番を作り、`60_revise.md` の指摘に従って振り直した。
→ 「章番号は識別子。**挿入ではなく末尾追加**。やむを得ず並べ替えたら、参照元を全文検索して直す」を明記。

## 2-8. 数値は1つの骨格表に集約する 〔優先度 B〕

資料ごとに数値を持つと、改訂のたびに一部が古いまま残る（実際に複数回発生）。
mfg では「数値骨格＝唯一の元」を定め、全資料をそこから作る形にした。
→ ドメインを問わず、「**同じ値が複数箇所に出るスキルは、元を1か所に決める**」は一般原則として書ける。

## 2-9. 既定値で進む設計は、確認すべき前提まで既定で埋めてしまう 〔優先度 B〕

「止まらずに進む」を優先した結果、題材が実在か架空か・実務用か教材用かといった
**間違えると全部やり直しになる前提**まで既定で決めていた。
→ 「既定値で進めてよい判断」と「**止まって確定させる判断**」の線引きを、スキル作成時に書かせる。
基準は「間違えたときの後戻りの大きさ」。

## 2-10. スキルの指示と、利用者のグローバル規約（CLAUDE.md）が衝突しうる 〔優先度 B〕

mfg は「次の1手を示す」と書いていたが、利用者のグローバル規約は「残作業の全体像を出してから聞く」。
衝突に気づかないまま両方に従おうとしていた。
→ スキル作成・改訂の手順に「**上位規約（CLAUDE.md・他スキル）と衝突しないか確認する**」を入れる。

## 2-11. 検証は作者以外（別セッション）で行う 〔優先度 A〕

私は利用者の指摘内容を覚えているので、規則が効いたのか記憶で補ったのか区別できない。
→ 「検証は**経緯を渡していないセッション**で、検証文書だけを見て実施する」を検証の章に。
そのためには検証文書が**単独で判定できる**必要がある（材料・手順・基準・記録表が全部そこにある）。
mfg ではこの書き直しを実際に求められた。

## 2-12. 大きな改訂は、原因ではなくコミット単位に分けないと検証できない 〔優先度 C〕

v1.8.3 は4コミットに分けた（入口／継ぎ目と数値／図とテンプレート／記録）。
分けたことで、どの変更がどの不具合に対応するかを後から追えた。
→ 「1コミットで2系統の変更をしない。**変更系統ごとに分け、CHANGELOG の行と対応させる**」を改訂手順に。

## 2-13. n を数えるには記録が要る。記録が止まると「直し方が間違っている」に気づけない 〔優先度 A〕

`60_revise.md` の「同じ原因が n≥3 なら対症療法ではなく根治」は、今回**実際に効いた**判断軸だった
（固定の表→組み立て手順への転換は、これで決めた）。
ただしそれは feedback に記録が積まれていたから成立した。2-5 の沈黙は、この判断軸ごと無効化する。
→ 記録の仕組みは、改善プロトコルの付録ではなく**中核**として扱う。

## 2-14. 実行副産物が配布フォルダに混ざる 〔優先度 C〕

`__pycache__` が `skills/` 配下に生成された。
→ スキル雛形の生成時点で `.gitignore` を入れる（スクリプトを assets に置くスキルでは必ず）。

## 2-15. レビューの指摘は、文脈を付けて記録しないと後で真逆に見える 〔優先度 C〕

利用者の「重み付き点数は一般的でない」と、のちの「総合は点数」は、
**セル（記号）と総合（点数）という別の話**だったが、記録に文脈が無く矛盾に見えた。
→ feedback の記録項目に「**どの場面での指摘か**」を必ず入れる。
